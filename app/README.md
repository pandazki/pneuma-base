# Pneuma Base 的 Mac 外壳（试做）

这个目录回答一个问题：把现有的管理界面（`pneuma-base view` 起的本机网页）放进一个 Swift 写的原生外壳里，能不能像一个常驻菜单栏的 Mac 应用那样好用、顺滑。它是试做，不是产品。代码只够回答这个问题，对库的每一次改动都经命令行做。

## 构建和打开

```sh
app/build.sh
open "app/dist/Pneuma Base.app"
```

`build.sh` 一条命令做完：命令行没构建过就先 `pnpm install` 和 `pnpm build`，再 `swift build -c release`，把可执行文件、`Resources/` 里的两个脚本、图标和 `Info.plist` 拼成 `app/dist/Pneuma Base.app`，最后用 `codesign --sign -` 做本机签名。双击 Finder 里的 `Pneuma Base.app` 也一样。

用 SwiftPM 而不是 Xcode 工程：没有 `.xcodeproj` 这种难审阅的文件，`swift build` 在命令行上每次得到一样的结果，不需要打开 Xcode 点任何东西。代价是 `.app` 由脚本拼装，资源文件不走 SwiftPM 的资源机制。

应用打开后只在菜单栏有一个图标（一个盒子）。第一次用：点它，选「新建或打开一个库…」，选一个空文件夹，它会被建成库，窗口随之打开。也可以启动时直接给一个库：

```sh
open "app/dist/Pneuma Base.app" --args --library ~/某个库
```

### 用的是哪个家目录

应用给它起的每个命令行进程设 `PNEUMA_BASE_HOME`。试做版缺省用 `app/.spike-home/`（不进 git），不碰真的 `~/.pneuma-base`。应用自己的小配置（认识哪些库、当前是哪个）和日志也在这里：`app/.spike-home/app/libraries.json`、`app/.spike-home/app/app.log`。

要用真的家目录，启动时说出来：

```sh
open "app/dist/Pneuma Base.app" --args --home ~/.pneuma-base
```

直接运行可执行文件时，环境变量 `PNEUMA_BASE_HOME` 也认。

## 五分钟试一试

1. 打开应用。看菜单栏出现盒子图标，Dock 里没有图标。
2. 点盒子 →「新建或打开一个库…」→ 新建一个空文件夹并选它。窗口打开，Dock 里出现图标。
3. 看窗口：红黄绿三个按钮在左边栏里；拖左边栏顶部、标题那一行，窗口跟着走；双击那一行，窗口按系统设置缩放。
4. 在系统设置里切换浅色和深色，窗口立刻跟着变。
5. 按 ⌘W 关掉窗口，Dock 图标消失；再点盒子 →「打开窗口」，看它回到原来的位置和大小，打开时没有白屏一闪。
6. 从 Finder 拖一个文件到窗口上，窗口出现「松开，放进库的 inbox/」，松开后页面跳到 `inbox/`，文件在里面，来历是「带进来的，主人给的」，出处是它原来所在文件夹的名字；从 Safari 下载的文件，出处是下载地址。
7. 再拖一个文件到菜单栏的盒子上，效果一样。
8. 在 Finder 里把一个文件复制进库的文件夹。约 6 秒后它被登记为主人带进来的，备注「自动登记」；菜单的「最近」顶上出现「刚才：已登记 1 个文件」，盒子图标变成实心的。用文本编辑器直接改一个已登记的文件，约 6 秒后记成主人改的。
9. 在页面上试 ⌘F（右上角出现搜索框）、⌘C、⌘V、⌘R（重新载入，在「显示」菜单里）、⌘[ 和 ⌘]（后退、前进）、右键（空白处没有菜单，选中的文字上是系统的文字菜单，没有「重新载入」和「检查元素」）。
10. 用 ⌘Q 退出，在终端里 `ps ax | grep "bin.js view"`，看不到它起的服务。

## 什么是真的，什么是假的

真的：菜单栏图标和它的菜单、窗口和它的原生外框、主菜单和快捷键、拖放、FSEvents 监看、子进程的启动、重启和退出。拖放和监看都经命令行写库（`put … --brought --by owner`、`say revised`），应用自己从不写库里的记录。

假的或凑合的：

- 命令行的位置是构建时写进 `Info.plist` 的（这个仓库的 `packages/cli/dist/bin.js`），Node 用 `/opt/homebrew/bin/node` 或 `/usr/local/bin/node`。正式版本要把一个 Node 和命令行的包放进 `.app` 里，见文末。
- 通知中心：代码按正式的做法写了（`UNUserNotificationCenter`，点通知打开窗口），但这台机器上系统拒绝了这个本机签名的应用（`Notifications are not allowed for this application`），一条通知也发不出去。作为替代，应用把最近一件事放在菜单「最近」的第一行，并把图标换成实心的，打开菜单后恢复。用开发者证书签名后大概能用，没有验证。
- 「最近」用的是 `check --since <30 天前> --json`，它列出除调用者以外的人做的事，所以主人自己的操作不在里面。
- 拖进来的东西一律放在库根的 `inbox/`，同名时按 Finder 的习惯加「 2」「 3」。
- 一次只有一个库在用：一个窗口、一个服务子进程、一个监看。换库时先停掉旧的。
- 应用里留着几个只给测量和检查用的钩子（分布式通知 `dev.pneumabase.spike`：打开、关闭、报进程号、把窗口挪到屏幕角落、切换深浅色、问一个点击归谁、查找、按菜单栏拖放的同一段代码放进一个文件），见 `App.swift` 末尾。

对网页的改动只有一处开关：应用载入网页时带 `?shell=mac`，网页据此在 `<html>` 上标 `data-shell`，给左边栏顶部留出红黄绿按钮的位置，把「用 pneuma-base view 启动」这类只对浏览器有意义的提示换掉，并让外框部分不能选中文字、不出现文字光标、整页不回弹。可以拖动窗口的区域由网页用 `data-drag` 标出，应用注入的 `Resources/shell.js` 把这些区域的位置报给原生的 `WKWebView` 子类，鼠标在这里按下就由系统拖窗口。浏览器里打开时没有 `shell=mac`，网页和以前一样。

## 数字

`app/measure.sh <库>` 量三轮，下面是在一个 8 样东西的小库上的结果。这台机器同时在跑别的测试和应用，负载 8 到 12（14 核），延迟的数字可能偏大。更早的一次三轮（脚本修正前）启动、打开窗口和窗口开着时的数字与这一次相差不到 15%。

| 量什么 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 怎么量的 |
| --- | --- | --- | --- | --- |
| 启动到菜单栏图标出现 | 192 ms | 189 ms | 188 ms | 从脚本调 `open` 到应用日志里「status item shown」的时刻。从内核起进程算起是 138、146、163 ms。图标真正画到菜单栏上还要再过一帧左右，没有量 |
| 「打开窗口」到页面画出，第一次 | 347 ms | 298 ms | 365 ms | 从 `openWindow()` 被调用，到窗口显示之后网页的第二个动画帧。服务在应用启动时就起好了 |
| 同上，第二次（关掉再开） | 239 ms | 227 ms | 247 ms | 同上。关窗口时网页进程被销毁，第二次要重新起一个 |
| 内存，窗口开着、空闲 | 129 MB | 128 MB | 129 MB | `footprint`：应用 24、Node 34、网页进程 43、WebKit 的 GPU 进程 20 到 21、网络进程 7 |
| 内存，没有窗口 | 56 MB | 58 MB | 55 MB | 关窗口 75 秒后：应用 21 到 23、Node 28、网络进程 6 到 7。网页进程随窗口销毁；GPU 进程在关窗口后约一分钟自己退出，网络进程在接下来的一分钟里也退出，之后只剩应用和 Node，约 50 MB |
| CPU，窗口开着空闲 60 秒 | 0.50% | 0.53% | 0.52% | `ps` 的累计 CPU 时间，60 秒前后相减，各进程相加（一个核的百分比）。Node 0.20%、网络进程 0.15 到 0.18%、网页进程 0.10%，都来自网页每 2 秒一次的查询；应用自己 0.05% |
| CPU，没有窗口空闲 60 秒 | 0.00% | 0.00% | 0.00% | 应用和 Node 在 60 秒里都没有用到 0.01 秒 CPU |
| 应用大小 | 724 KB | | | `du -sh`，其中图标 181 KB |

打开窗口的时间花在哪：在一次测量的日志里，第一次打开到网页文档载完 192 ms（起网页进程、取 HTML 和脚本），到内容就绪 327 ms（网页再向服务要两次数据，服务每次都重新打开库），到画出 413 ms；第二次是 123、184、237 ms。第一次多出来的，推测主要是 WebKit 起 GPU 和网络两个进程。

量的过程里出过一次错，记在这里：第一版脚本在 GPU 进程中途退出后把它一生用过的 CPU 当成了 60 秒里用的，报出约 0.85%。脚本现在对退出的进程写「exited」。

## 核对过的和要人来看的

`app/verify.sh` 在临时文件夹里建一个新库，打开应用，逐条核对：服务是应用的子进程；用 `cp` 复制进去的文件被登记为主人带进来的（打印 `inspect`）；用 `xattr` 写了下载地址的文件，出处是那个地址；经菜单栏拖放的同一段代码放进去的文件在 `inbox/`，出处是文件夹名；agent 放的 5 个文件都还是 agent 的；退出和 `kill -9` 之后都不留进程（先核对检查本身在应用开着时看得到进程）。另外核对过：杀掉服务子进程，0.5 秒后重启，开着的窗口换新地址重新载入；窗口截图（浅色，和切到深色之后）；标了 `data-drag` 的点击由网页视图收到并判为拖窗口，按钮和内容区不判；⌘F 在页面上找到并选中文字。

要人来看的：真的用鼠标拖窗口和双击；从 Finder 真的拖文件到窗口和菜单栏图标上（拖放之后的代码核对过，拖放本身的那一层没有）；系统切换深浅色时（核对的是应用自己切换）；Dock 图标随窗口出现和消失；右键菜单的样子；⌘F 选中的文字在前台窗口里的高亮；通知（系统拒绝，见上）。

## 监看和 agent 自己的放入

agent 放东西时，内核先把文件改名放到目标路径，然后记账插件才写下记录。这中间文件已经在库里，却没有人登记，监看如果正好这时去看，会把它当成主人复制进来的。

实验（`app/experiments/put-race.mjs`，可以重跑）：

- `window` 模式一边让 agent 一个接一个地放文件，一边尽快轮询目标文件和记账的事实文件。文件出现到第一条新事实之间就是这段空档。空档确实存在，而且随记账的事实变多而变长，因为记账插件每次写之前要读全部事实：

  | 库里的事实文件 | 小文件（30 次） | 50 MB 的文件（10 次） |
  | --- | --- | --- |
  | 约 40 个 | 中位 4.7 ms，最长 10.6 ms | 中位 28 ms，最长 32 ms |
  | 约 600 个 | 中位 28.5 ms，最长 52.7 ms | 中位 53 ms，最长 60 ms |

  照这个斜率，几万条事实的库会到秒级；机器很忙时也会更长。所以监看不能一看到文件就登记。
- `app` 模式在应用开着时让 agent 按说明从库外放 20 个文件：20 个都还是 agent 做出来的，监看一个也没碰。再让它违反说明，用自己的写文件工具在库里直接写一个文件、隔一段时间才登记，四轮各隔 2、5、10、20 秒：隔 2 秒和 5 秒的仍是 agent 的；隔 10 秒和 20 秒的，监看在约 6 秒时已把它登记成主人带进来的。跑了两次，结果一样。

监看用的规则：只看监看开始后有过事件的路径；整个库（含 `.pneuma-base/`）安静 3 秒、应用自己没有正在进行的放入时才去 `check`；同一个文件要在相隔至少 3 秒的两次 `check` 里都没人登记、大小和修改时间都没变，才登记成主人的。照上面量到的空档，这给按说明放入的 agent 留了 100 倍以上的余量。登记时如果发现别人刚刚登记过（`put` 答「已在册」），只算加了备注，不算登记。

弱点是它只看时间：agent 违反说明，在库里直接写文件、又在 6 秒以后才登记，这个文件就会被当成主人的；agent 之后的 `put --made` 只会在上面加一条备注，来历不会改回来。这个漏洞靠时间堵不上，要么让内核在改名之前先写下「正在放入」，要么让 agent 根本没有库目录的写权限。

## 哪里还不像原生

已经是原生的：窗口和外框（红黄绿按钮、全屏、拼贴、调度中心、位置大小记住）、菜单栏图标和菜单、主菜单和快捷键、⌘F 的搜索框（原生工具栏搜索项，查找交给 `WKWebView.find`）、滚动（WebKit 用系统的惯性滚动和浮动滚动条）、文字渲染（CoreText）、选中文字时的右键菜单（系统的拷贝、查询、翻译）。下面这些还看得出是网页，每一条写明在这个方案里能不能补上。

| 哪里 | 现在 | 能不能补 |
| --- | --- | --- |
| 字体 | 网页用 Inter，系统应用用苹方和 SF Pro，字形和字距都不同 | 能。外壳模式下把 `--font-sans` 换成 `system-ui`，一行 CSS |
| 强调色 | 网页固定用自己的蓝色，不跟系统设置里的强调色和高亮色 | 能。外壳模式下用 WebKit 认的 `AccentColor`、`-apple-system-*` 颜色 |
| 左边栏的材质 | 网页画的平的灰色；系统的边栏是半透明的，macOS 26 上还是浮起来的玻璃 | 半透明能补：网页让边栏透明，外壳在网页下面垫一个 `NSVisualEffectView`。浮起的玻璃边栏补不上，要原生视图 |
| 窗口失去焦点时 | 系统应用的边栏选中项和控件会变灰，网页不知道窗口是不是在前面 | 能。外壳把窗口的前后状态告诉网页，网页换样式 |
| 控件 | 分段选择、按钮、焦点框、悬停高亮都是网页画的；系统的边栏没有悬停高亮，焦点框也不是这个样子 | 大部分能靠外壳模式的 CSS 拉近，做不到一模一样。要一模一样就得用原生控件 |
| 列表的键盘操作 | 表格行只能用 Tab 走，没有上下键选中、按字母跳转、空格预览 | 能，在网页里写；空格预览用外壳调系统的快速查看（`QLPreviewPanel`） |
| 拖出去 | 不能把一行拖到 Finder 或别的应用里 | 能。网页告诉外壳从哪一行开始拖，外壳用 `NSDraggingSession` 拖出真的文件 |
| 行上的右键菜单 | 没有（空白处的浏览器菜单去掉了）；系统应用在行上给「在 Finder 中显示」「归档」 | 能。网页把要显示的菜单项交给外壳，外壳弹 `NSMenu` |
| 打开窗口的速度 | 0.23 到 0.37 秒才画出内容（见上面的数字）；原生窗口几乎是立刻的 | 部分能。关窗口时留着网页不销毁，第二次打开就是立刻的，代价是一个网页进程的内存和每 2 秒一次的查询 |
| 刷新 | 网页每 2 秒问一次库有没有变 | 能。外壳已经在用 FSEvents 监看，可以把变化直接推给网页，不用轮询 |
| 内存 | 窗口开着时应用、Node、网页进程、GPU 进程、网络进程加起来约 130 MB；同样功能的原生应用估计 40 MB 上下（推测，没有量） | 不能根本改变。Node 和 WebKit 的几个进程是这个方案的底数 |
| 通知 | 本机签名的应用被系统拒绝，见上面 | 和方案无关，正式签名的问题 |

我的判断：内容区（表格、详情面板、对话框）在这个方案里能做到一般人分不出来；做不到「分不出来」的是外框里的那几样：浮起的玻璃边栏、原生控件的手感、列表的键盘和拖放习惯。它们单独看都能用网页模仿个大概，但每一样都是在网页里重写一遍 AppKit 已经有的行为，越往细处越贵，也永远差一点。所以 1.0 建议改成混合的：边栏和工具栏用原生视图（`NSSplitViewController` 的边栏、`NSOutlineView`、`NSToolbar`），内容区留网页；外壳和网页之间就是这次试出来的这几条消息（拖动区域、画好了、拖放、查找），再加上导航和选中。

## 正式版本要带什么

- 一个 Node：这台机器上找到的一个独立的 Node 24（darwin-arm64，静态链接，不依赖 Homebrew 的库）是 126,827,136 字节，约 121 MiB。Homebrew 的 Node 不能直接放进去：它的 `node` 只有 130 KB，其余在 61 MB 的 `libnode` 和几十个 Homebrew 的动态库里。要同时支持 Intel 再翻一倍。
- 命令行和它带的包：`packages/*/dist` 合起来 2.7 MB（含声明文件和 source map），没有第三方的运行时依赖。`pnpm pack:dist` 打出的命令行包就是要放进去的东西。
- 应用找命令行和 Node 的位置改成 `.app` 里的相对路径，不再是构建时写死的绝对路径。
- 开发者证书签名和公证，否则通知发不出去，别人的机器上也打不开。
- 缺省的家目录换成真的 `~/.pneuma-base`，去掉 `app/.spike-home` 和测试钩子。

这样一个 `.app` 约 122 MB，几乎全是 Node。
