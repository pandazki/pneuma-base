# Pneuma Base 的 Mac 外壳

一个 Swift 写的原生外壳，里面是现有的管理界面（`pneuma-base view` 起的本机网页）。它把主人要走的那条路接起来：选一个文件夹，把资料放进去，一个一个接上 agent，开始干活；其余时候待在菜单栏里。

应用自带一个 Node 和命令行（连同管理界面和五个自带的插件），下载下来什么都不用另装。外壳不持有库的状态。它只记得这台机器认识哪些库、当前是哪个、它自己的设置；对库做的每一件事都经它自带的命令行做。没有开发者证书签名，别人下载后第一次打开要多走几步，见文末「发给别人」。

## 构建和打开

```sh
app/build.sh --node <一个独立的 node>      # 或设 PNEUMA_BASE_NODE；都不给就用 PATH 上的 node
open "app/dist/Pneuma Base.app"
app/build.sh --node <…> --dist             # 另打一个 zip，给别人下载
```

`build.sh` 一条命令做完：`pnpm build`（没装依赖就先 `pnpm install`），`swift build -c release`，再用 `scripts/pack-dist.mjs` 打出命令行的包文件、解开放进应用，拼成 `app/dist/Pneuma Base.app`，最后用 `codesign --sign -` 做本机签名。双击 Finder 里的 `Pneuma Base.app` 也一样。

应用里有什么：

| 位置 | 是什么 | 大小 |
| --- | --- | --- |
| `Contents/MacOS/Pneuma Base` | 外壳 | 0.7 MB |
| `Contents/MacOS/node` | 构建时找到的那个 Node，原样拷进来，保留它自己的签名 | 117 MB |
| `Contents/Resources/cli/` | 命令行的包：`dist/bin.js`，`node_modules/` 里的内核、sdk、管理界面和五个自带插件，`PLUGINS.md`、`LICENSE`、`NOTICE` | 2.5 MB |
| `Contents/Resources/` 其余 | 图标、`shell.js`、`parent-watch.mjs` | 0.2 MB |

合起来 120 MB（`du -sh`），zip 是 39 MB。Node 要合两条：不低于命令行的 Node 下限（`packages/cli/src/node-floor.ts`，`build.sh` 用它自己核），只依赖 macOS 自己的库（`otool -L` 里只有 `/usr/lib/` 和 `/System/Library/`）。nodejs.org 的构建合；Homebrew 的不合（它的 `node` 只有 130 KB，其余在 `libnode` 和几十个 Homebrew 的动态库里），`build.sh` 拒绝它，并给出同版本的 nodejs.org 下载地址。构建出来的应用只是这台机器的架构（`lipo -archs` 印在最后一行）。

能变小的地方（量过的标「量过」）：

- `strip -x` 去掉 Node 的本地符号：122.6 MB 变成 98.4 MB（量过），去掉之后照样能跑命令行（量过），zip 只小 3 到 4 MB（量过）。代价是 Node 自己的签名没了（要重签），崩溃时的调用栈没有名字。没有做。
- 自己编一个 Node：只带少量 ICU（`--with-intl=small-icu`）、不带调试器（`--without-inspector`）。估计能再小 25 到 30 MB（推测，没有编过）；代价是要维护一条 Node 的构建，`Intl` 只认英文。
- 同时支持 Intel 要把两个 Node 合成一个通用的，Node 那一份翻一倍。

用 SwiftPM 而不是 Xcode 工程：没有 `.xcodeproj` 这种难审阅的文件，`swift build` 在命令行上每次得到一样的结果，不需要打开 Xcode 点任何东西。代价是 `.app` 由脚本拼装，资源文件不走 SwiftPM 的资源机制。

第一次打开、还没有库时，只出一个小窗口：两句话和「选一个文件夹…」。选的文件夹不是库就建成库，然后主窗口打开在它的首页上，首页最上面是「开始」。之后应用待在菜单栏里（一个盒子）：点它是一个小面板，右键是库的菜单。也可以启动时直接给一个库：

```sh
open "app/dist/Pneuma Base.app" --args --library ~/某个库
```

### 用的是哪个家目录

应用给它起的每个命令行进程设 `PNEUMA_BASE_HOME`，缺省是真的 `~/.pneuma-base`，和从包装的命令行是同一个。应用自己的小配置（认识哪些库、当前是哪个、这台机器的设置）和日志在它的 `app/` 里：`~/.pneuma-base/app/libraries.json`、`~/.pneuma-base/app/app.log`。

启动时给 `--home` 换一个，或者设环境变量 `PNEUMA_BASE_HOME`：

```sh
open "app/dist/Pneuma Base.app" --args --home /tmp/试一试
```

`verify.sh` 和 `measure.sh` 总是用临时的家目录。

### 本机的命令

应用每次启动都跑一次自带命令行的 `launcher install`：让 `~/.pneuma-base/bin/pneuma-base` 指向应用里的 Node 和命令行。它是一个小脚本：

```sh
#!/bin/sh
# 这台机器上的 pneuma-base。接上的 agent 按这个路径运行它，路径不变，内容由提供命令行的一方保持最新：
# Pneuma Base 应用每次启动时，或 pneuma-base launcher install。
PNEUMA_BASE_HOME='/Users/<你>/.pneuma-base'
export PNEUMA_BASE_HOME
exec '/Applications/Pneuma Base.app/Contents/MacOS/node' '/Applications/Pneuma Base.app/Contents/Resources/cli/dist/bin.js' "$@"
```

接上 agent 时写进去的（技能里的命令行、MCP 条目的 `command`）都按绝对路径写这个脚本，所以 agent 的 PATH 上什么都不用有，也找得到授权所在的家目录。应用挪了位置或换了新版，下次启动时脚本跟着改，接上的 agent 不用重接。内容没变就不写。不要管理员权限，不改 PATH。

macOS 把从解压出来的地方直接打开的下载应用放在一个临时的位置运行（App Translocation），退出后那个位置就没了，脚本指向那里就会断。应用看到自己在这样的位置上，会先说：把它拖进「应用程序」文件夹再从那里打开，可以退出，也可以先这样用。

### 设置

「Pneuma Base › 设置…」（⌘,）或菜单栏图标的右键菜单打开设置窗口，都是这台机器的设置：

- **直接放进来的文件算主人的**：和菜单里那一项是同一个，缺省开着。
- **在终端里用 pneuma-base**：缺省关着。打开时，在你选的一个文件夹里放一个叫 `pneuma-base` 的符号链接，指向本机的命令；可选的是你的 PATH 上你能写的文件夹（问你的登录 shell 要 PATH，三秒没答复就用应用自己的）。那里已经有一个不是这里放的 `pneuma-base`，不动它，说出来。一个能写的都没有时，给出要加进 shell 配置文件的那一行（`export PATH="$HOME/.pneuma-base/bin:$PATH"` 这样的），只显示，不写。关掉时，链接还指向本机的命令才拿走。
- **登录时打开**：缺省关着，用系统的 `SMAppService.mainApp`。这台机器的规矩不许真的装登录项，所以注册这一步没有试过；没签名的应用上系统答应不答应，没有验证。系统要你在「系统设置 › 通用 › 登录项」里允许时，设置里会说。
- 最下面写着本机的命令在哪。

## 五分钟试一试

1. 打开应用。没有库时出来一个小窗口，两句话和「选一个文件夹…」。菜单栏出现盒子图标。
2. 点「选一个文件夹…」，新建一个空文件夹并选它。小窗口关掉，主窗口打开在首页，最上面是「开始」：做完了 0 步，还有 3 步。
3. 第一步「接上你的 agent」列出这台机器上找到的产品，每个一行。点一个的「接上」，不出表单，一下就接上了，这一步折成一行「已接上 …」。装进去的技能和 MCP 条目都写本机的命令的完整路径，agent 那边不用另装什么。
4. 第二步「放进第一样东西」是一块虚线的区域。从 Finder 拖一个文件到窗口的任何地方，窗口出现「松开，放进库的 inbox/，记成你带进来的」，松开后右下角一条提示，这一步折成「库里有 1 样东西」。点区域里的「选择…」，可以选文件和文件夹，效果一样。窗口开在库页的某个文件夹上时，拖进来的放进那个文件夹。
5. 第三步是一句可以复制的话。在接上的 agent 里说它；agent 在库里做过一件事，「开始」就没了。
6. 点菜单栏的盒子：一个小面板，顶上是库名，然后是等你决定的前三件（在这里就能回答）和自上次以来的最新几行，底下「打开窗口」「退出」。有事等你时，盒子右上角有一个点。右键盒子是库的菜单：换库、新建或打开一个库、打开窗口、「直接放进来的文件算主人的」、退出。
7. 在 Finder 里把一个文件复制进库的文件夹。库里安静 3 秒后它被登记为主人带进来的（自动登记）；窗口开着时右下角一条提示，没开时是一条通知（这台机器上发不出去，见下）。用文本编辑器直接改一个已登记的文件，同样记成看到的改动。在「Pneuma Base」菜单或右键菜单里关掉「直接放进来的文件算主人的」，就不再自动登记。
8. 在系统设置里切换浅色和深色，窗口和面板立刻跟着变。按 ⌘W 关掉窗口，Dock 图标消失；点面板的「打开窗口」，它回到原来的位置和大小。
9. 在页面上试 ⌘F（右上角出现搜索框）、⌘C、⌘V、⌘R（重新载入，在「显示」菜单里）、⌘[ 和 ⌘]（后退、前进）。
10. 用 ⌘Q 或面板的「退出」退出，在终端里 `ps ax | grep "bin.js view"`，看不到它起的服务。

## 什么是真的，什么是假的

真的：第一次的小窗口，菜单栏图标、它的面板和右键菜单，窗口和它的原生外框、主菜单和快捷键、拖放和选文件、FSEvents 监看、子进程的启动、重启和退出。拖放、选文件和监看都经命令行写库（`put … --brought --by owner`，监看另加 `--observed`；`say revised --observed`），应用自己从不写库里的记录。

- 面板是网页的一种排法（`?shell=mac&panel=tray`），装在 `NSPopover` 里。它的网页视图第一次打开面板时才造，之后留着，所以再打开是立刻的；面板不显示时网页不问服务。面板告诉应用它的内容多高，应用照着定面板的高。
- 图标上的点：应用数首页上等主人决定的事（`show home --json` 里所有 `asks` 块的件数）。库里一有变化（监看看到的任何事件，含 agent 写的记录）就在 1.5 秒后数一次，放完东西数一次，另外每分钟一次；面板开着时用面板说的数。
- 「直接放进来的文件算主人的」是这台机器的设置，缺省开着，记在应用的小配置里（`ownerFiles`），不在库里。
- 拖进来、选进来的东西放进窗口正在看的文件夹（地址里的 `view.dir`，库页和文件页都用它），没有就放进库根的 `inbox/`；同名时按 Finder 的习惯加「 2」「 3」。出处是 macOS 记下的下载地址，没有就是它原来所在文件夹的名字。

假的或凑合的：

- 签名是本机签名（ad hoc），见文末「发给别人」。
- 通知中心：代码按正式的做法写了（`UNUserNotificationCenter`，点通知打开窗口），但这台机器上系统拒绝了这个本机签名的应用（`Notifications are not allowed for this application`），一条通知也发不出去。窗口开着时，同样的话改成网页右下角的一条提示，这一条是能用的。用开发者证书签名后通知大概能用，没有验证。
- 一次只有一个库在用：一个窗口、一个服务子进程、一个监看。换库时先停掉旧的。
- 应用里留着只给测量和检查用的钩子，只在启动时带 `--hooks <名字>` 才听，听的是分布式通知 `dev.pneumabase.hooks.<名字>`，检查脚本只驱动它自己起的那一份。能做的：打开、关闭、退出、报进程号、把窗口挪到屏幕角落、切换深浅色、问一个点击归谁、查找、像选了一个文件夹那样打开库、按拖到菜单栏图标或窗口上的同一段代码放进一个文件、点图标、把窗口或面板的文字写到文件、给窗口、面板、第一次的小窗口、设置窗口拍一张图、打开设置、像那个开关一样放上和拿走 PATH 上的链接、把设置写成字。见 `App.swift` 末尾。

网页这边有两处开关。应用载入网页时带 `?shell=mac`，网页据此在 `<html>` 上标 `data-shell`，改用系统字体，给左边栏顶部留出红黄绿按钮的位置（边栏收成一列图标时也留着），把「用 pneuma-base view 启动」这类只对浏览器有意义的提示换掉，并让外框部分不能选中文字、不出现文字光标、整页不回弹。窗口成为或不再是前台窗口时，应用在网页里发一个 `pneuma-shell` 事件，带 `{ window: 'active' }` 或 `{ window: 'inactive' }`，网页内容就绪时也发一次；网页据此在 `<html>` 上标 `data-window`，窗口在后面时把边栏的选中项、图标、标签和标题调淡，像系统的窗口那样。可以拖动窗口的区域由网页用 `data-drag` 标出，应用注入的 `Resources/shell.js` 把这些区域的位置报给原生的 `WKWebView` 子类，鼠标在这里按下就由系统拖窗口。浏览器里打开时没有 `shell=mac`，网页和以前一样。面板再带 `panel=tray`。网页和外壳之间的每一条消息写在 `ARCHITECTURE.md` 的「界面的外壳」里。

## 数字

`app/measure.sh <库>` 量三轮，下面是在一个 8 样东西的小库上的结果。这台机器同时在跑别的测试和应用，负载 8 到 12（14 核），延迟的数字可能偏大。更早的一次三轮（脚本修正前）启动、打开窗口和窗口开着时的数字与这一次相差不到 15%。这些数字是应用自带 Node 之前量的（那时用 Homebrew 的 Node 26），换成自带的 Node 24 之后没有重量；应用大小是现在的。

| 量什么 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 怎么量的 |
| --- | --- | --- | --- | --- |
| 启动到菜单栏图标出现 | 192 ms | 189 ms | 188 ms | 从脚本调 `open` 到应用日志里「status item shown」的时刻。从内核起进程算起是 138、146、163 ms。图标真正画到菜单栏上还要再过一帧左右，没有量 |
| 「打开窗口」到页面画出，第一次 | 347 ms | 298 ms | 365 ms | 从 `openWindow()` 被调用，到窗口显示之后网页的第二个动画帧。服务在应用启动时就起好了 |
| 同上，第二次（关掉再开） | 239 ms | 227 ms | 247 ms | 同上。关窗口时网页进程被销毁，第二次要重新起一个 |
| 内存，窗口开着、空闲 | 129 MB | 128 MB | 129 MB | `footprint`：应用 24、Node 34、网页进程 43、WebKit 的 GPU 进程 20 到 21、网络进程 7 |
| 内存，没有窗口 | 56 MB | 58 MB | 55 MB | 关窗口 75 秒后：应用 21 到 23、Node 28、网络进程 6 到 7。网页进程随窗口销毁；GPU 进程在关窗口后约一分钟自己退出，网络进程在接下来的一分钟里也退出，之后只剩应用和 Node，约 50 MB |
| CPU，窗口开着空闲 60 秒 | 0.50% | 0.53% | 0.52% | `ps` 的累计 CPU 时间，60 秒前后相减，各进程相加（一个核的百分比）。Node 0.20%、网络进程 0.15 到 0.18%、网页进程 0.10%，都来自网页每 2 秒一次的查询；应用自己 0.05% |
| CPU，没有窗口空闲 60 秒 | 0.00% | 0.00% | 0.00% | 应用和 Node 在 60 秒里都没有用到 0.01 秒 CPU |
| 应用大小 | 120 MB | | | `du -sh`，其中 Node 117 MB，见上面「应用里有什么」；zip 39 MB |

打开窗口的时间花在哪：在一次测量的日志里，第一次打开到网页文档载完 192 ms（起网页进程、取 HTML 和脚本），到内容就绪 327 ms（网页再向服务要两次数据，服务每次都重新打开库），到画出 413 ms；第二次是 123、184、237 ms。第一次多出来的，推测主要是 WebKit 起 GPU 和网络两个进程。

量的过程里出过一次错，记在这里：第一版脚本在 GPU 进程中途退出后把它一生用过的 CPU 当成了 60 秒里用的，报出约 0.85%。脚本现在对退出的进程写「exited」。

## 核对过的和要人来看的

`app/verify.sh` 沿新主人走的那条路核对构建好的应用，用临时的 `HOME` 和临时的 `PNEUMA_BASE_HOME`（`open -n --env`），不读不写这台机器上真的 agent 配置和库。它用的命令行就是应用自带的 Node 和命令行，PATH 上只有系统工具。它起的那一份应用带自己的钩子名，按钩子名找进程、停进程，从不按应用的名字退出别的那一份。逐条核对：

- 第一次启动写好本机的命令，指向应用里的 Node 和命令行、导出这个家目录；服务进程跑的也是应用里的 Node 和命令行。
- 没有库时第一次打开，出来小窗口；像选了一个文件夹那样（钩子，走同一段代码），文件夹被建成库，主窗口打开，服务是应用的子进程，首页最上面是「开始」，做完了 0 步，还有 3 步。
- 经拖到窗口上的同一段代码放进一个文件：在 `inbox/`，「带进来的，主人给的 · 主人」，出处是文件夹名；第二步折成「库里有 1 样东西」。窗口开在库页的 `docs/` 上时，拖进来的放进 `docs/`；拖到菜单栏图标上的进 `inbox/`。
- 直接写进库里的文件被监看登记成「带进来的，主人给的（自动登记）」；用 `xattr` 写了下载地址的，出处是那个地址；直接改一个已登记的文件，记成「直接改的，自动登记」。
- 假的 `~/.claude`（在临时 `HOME` 里）让第一步列出 Claude Code；`agent connect claude-code` 把技能写进临时 `HOME`，第一步折成「已接上 Claude Code」。
- 技能里的三行命令（start、put、find）都以本机的命令的完整路径开头；把占位换掉，用 `env -i`、PATH 只有 `/usr/bin:/bin`、不设 `PNEUMA_BASE_HOME`，像 Claude Code 那样经 `sh -c` 原样跑，三行都成；放进去的那样东西是「做出来的 · claude-code」，场景是 start 说的那句。
- 假的 Claude Desktop 接上之后，它的 MCP 条目是 `<本机的命令> @claude-desktop mcp`，没有 `env`；用 `env -i` 照条目起它，`initialize`、`tools/list` 得到全部工具，经它 `put` 的东西是 Claude Desktop 的。
- agent 放的 5 个文件都还是 agent 的，监看一个也没登记。
- agent 说一个站点可以部署之后，图标上出现点；首页的「开始」没了（有 agent 做过事了）；点图标打开面板，面板里有库名、那件要决定的事和「打开窗口」。
- 设置：两个方便的开关都是关着的，登录时打开也是；PATH 上能写的文件夹里有 `verify.sh` 放进应用 PATH 的那个；打开「在终端里用 pneuma-base」（钩子，走同一段代码）后那里有一个指向本机的命令的链接，`env -i` 加那个文件夹在终端里直接打 `pneuma-base` 能用；关掉后链接没了。
- 退出之后应用和服务都不在。
- 把应用拷到别处再打开：本机的命令改指向那一份里的 Node，技能和 MCP 条目一个字都没变，照样能用；把那一份挪走，`agent list` 说命令指向的 Node 不在了；再打开原来的应用，命令修好，每个连接都在用。
- `kill -9` 之后服务也不在。
- 设了 `PNEUMA_BASE_SHOTS` 时，给第一次的小窗口、面板和设置窗口各拍浅色、深色两张。小窗口的图带标题栏；面板的图只有网页的内容，铺在窗口的底色上，没有弹出框的外框和箭头。

要人来看的：从网上真的下载 zip、第一次打开（见「发给别人」），和没拖进「应用程序」就打开时的那句提醒（App Translocation 在这里造不出来，判断只是看路径里有没有 `/AppTranslocation/`）；在真的 Claude Code 里说那一句话；登录时打开；在真的 PATH 文件夹里放链接；真的用鼠标拖窗口和双击；从 Finder 真的拖文件到窗口和菜单栏图标上，和「选择…」弹出的面板（拖放和选文件之后的代码核对过，拖放本身和面板那一层没有）；面板在菜单栏下的位置、点图标开关面板、右键菜单的样子；系统切换深浅色时（核对的是应用自己切换）；Dock 图标随窗口出现和消失；⌘F 选中的文字在前台窗口里的高亮；通知（系统拒绝，见上）。

## 监看和 agent 自己的放入

agent 放东西时，内核先把文件放到目标路径，然后记账插件才写下记录。这中间文件已经在库里，却没有人登记。以前的监看只能靠时间躲开这段空档：库里安静 3 秒才看，同一个文件要在相隔至少 3 秒的两次 `check` 里都没人登记、大小和修改时间都没变，才登记成主人的。现在内核在放动手之前为它的路径写一个「正在放入」的标记（`ARCHITECTURE.md` 第 4 节），对账读过文件之后再读标记、再读事实，正在放的路径和对账期间有了记录的路径都不报。所以「这个文件有没有人登记」只问记账插件，监看不再自己看两次。

监看现在的规则：

1. 只看上次看过之后有过事件的路径（库里的文件，不含 `.pneuma-base/`、`PNEUMA-BASE.md`、归档区和 `.DS_Store`）。
2. 等整个库（含 `.pneuma-base/`）安静 3 秒，这是为了不把主人还在复制的文件拿走一半。
3. 读一次 `show ledger.standing --json`（不用 `check`：主人的 `check` 会记一条「看过了」，把首页的「自上次以来」清掉）。
4. 「没人登记过的」里的、第 1 条里有的路径，`put <路径> --brought --by owner --observed --note 自动登记`，有下载地址的加 `--source`；「被直接改过的」里的，`say revised <路径> --observed`。
5. 如果在这次看和这次放之间别人登记了它，`put` 答「已在册」，只算加了一条备注。

agent 违反说明、在库里直接写文件又过了几秒才登记的，监看会先把它登记成主人带进来的（看到的）；agent 之后的 `put --made` 是说的，盖过看到的，来历改成 agent 做出来的，看到的那条留在「先前」里。

实验（`app/experiments/put-race.mjs`，可以重跑）：

- `window` 模式量这段空档：文件出现到第一条新事实之间。试做时量过：约 40 个事实文件的库上，小文件中位 4.7 ms、最长 10.6 ms，50 MB 的文件中位 28 ms、最长 32 ms；约 600 个事实文件时，小文件中位 28.5 ms、最长 52.7 ms，50 MB 的中位 53 ms、最长 60 ms。空档随事实变多而变长，几万条事实的库会到秒级。
- `marks` 模式不开应用，一边让 agent 一个接一个地放 40 个文件（10 个 50 MB），一边用两个读者背靠背地读状况页，和监看读的一样。这一次的空档中位 2.6 ms，最长 30 ms。94 次读里有 58 次是在某个放进行时读的，54 次的时间跨过了某个文件已经在位、还没有记录的时刻；放的文件一次也没有出现在「没人登记过的」里。对照：同时在库里直接写的 5 个文件（没有放），5 个都被读者列成没人登记的。
- `app` 模式开着应用，agent 按说明从库外放 30 个文件（10 个 50 MB），每次前停 2.8 到 3.8 秒，正好是监看等安静的时长，让它的看落在放上：监看在这期间看了 20 次，其中 8 次和一个正在进行的放重叠；30 个都还是 agent 做出来的，没有一个先被监看登记过。再让 agent 在库里直接写文件、隔 1、2、5、10、20 秒才登记：隔 1 秒和 2 秒的，监看还没看，直接是 agent 的；隔 5、10、20 秒的，监看先登记成主人带进来的（看到的），agent 的 `put` 随后把来历改成 agent 做出来的。每个路径都只有一样东西，最后都是 agent 的，没有重复登记。

## 哪里还不像原生

已经是原生的：窗口和外框（红黄绿按钮、全屏、拼贴、调度中心、位置大小记住）、菜单栏图标和菜单、主菜单和快捷键、⌘F 的搜索框（原生工具栏搜索项，查找交给 `WKWebView.find`）、滚动（WebKit 用系统的惯性滚动和浮动滚动条）、文字渲染（CoreText）、选中文字时的右键菜单（系统的拷贝、查询、翻译）。下面这些还看得出是网页，每一条写明在这个方案里能不能补上。

| 哪里 | 现在 | 能不能补 |
| --- | --- | --- |
| 字体 | 已补：外壳模式下 `--font-sans` 是系统字体（SF Pro 和苹方），表格量列宽也按它量 | — |
| 强调色 | 网页没有自己的强调色：主要按钮近黑，蓝色只给键盘焦点和「进行中」；不跟系统设置里的强调色和高亮色 | 能。外壳模式下把 `--focus` 换成 WebKit 认的 `AccentColor` |
| 左边栏的材质 | 网页画的平的灰色；系统的边栏是半透明的，macOS 26 上还是浮起来的玻璃 | 半透明能补：网页让边栏透明，外壳在网页下面垫一个 `NSVisualEffectView`。浮起的玻璃边栏补不上，要原生视图 |
| 窗口失去焦点时 | 已补：外壳把窗口的前后状态告诉网页（上面的 `pneuma-shell` 事件），边栏的选中项和图标变淡 | — |
| 控件 | 分段选择、按钮、焦点框、悬停高亮都是网页画的；系统的边栏没有悬停高亮，焦点框也不是这个样子 | 大部分能靠外壳模式的 CSS 拉近，做不到一模一样。要一模一样就得用原生控件 |
| 列表的键盘操作 | 表格里上下键、Home、End 在行之间走，回车打开，只有一行在 Tab 的顺序里；边栏的页也用上下键走。没有按字母跳转和空格预览 | 能，在网页里写；空格预览用外壳调系统的快速查看（`QLPreviewPanel`） |
| 拖出去 | 不能把一行拖到 Finder 或别的应用里 | 能。网页告诉外壳从哪一行开始拖，外壳用 `NSDraggingSession` 拖出真的文件 |
| 行上的右键菜单 | 没有（空白处的浏览器菜单去掉了）；系统应用在行上给「在 Finder 中显示」「归档」 | 能。网页把要显示的菜单项交给外壳，外壳弹 `NSMenu` |
| 打开窗口的速度 | 0.23 到 0.37 秒才画出内容（见上面的数字）；原生窗口几乎是立刻的 | 部分能。关窗口时留着网页不销毁，第二次打开就是立刻的，代价是一个网页进程的内存和每 2 秒一次的查询 |
| 刷新 | 网页每 2 秒问一次库有没有变 | 能。外壳已经在用 FSEvents 监看，可以把变化直接推给网页，不用轮询 |
| 内存 | 窗口开着时应用、Node、网页进程、GPU 进程、网络进程加起来约 130 MB；同样功能的原生应用估计 40 MB 上下（推测，没有量） | 不能根本改变。Node 和 WebKit 的几个进程是这个方案的底数 |
| 通知 | 本机签名的应用被系统拒绝，见上面 | 和方案无关，正式签名的问题 |

我的判断：内容区（表格、详情面板、对话框）在这个方案里能做到一般人分不出来；做不到「分不出来」的是外框里的那几样：浮起的玻璃边栏、原生控件的手感、列表的键盘和拖放习惯。它们单独看都能用网页模仿个大概，但每一样都是在网页里重写一遍 AppKit 已经有的行为，越往细处越贵，也永远差一点。所以 1.0 建议改成混合的：边栏和工具栏用原生视图（`NSSplitViewController` 的边栏、`NSOutlineView`、`NSToolbar`），内容区留网页；外壳和网页之间就是这次试出来的这几条消息（拖动区域、画好了、拖放、查找），再加上导航和选中。

## 发给别人

`app/build.sh --node <…> --dist` 在 `app/dist/` 里打一个 zip（`ditto -c -k --keepParent`），39 MB。应用只有本机签名（ad hoc），没有开发者证书，没有经过 Apple 公证。下面按 Apple 的说明写，没有在别的机器上从网上下载点过一遍。

别人下载之后，在现在的 macOS（15 和 26）上第一次打开要做的：

1. 双击 zip 解开，把「Pneuma Base」拖进「应用程序」文件夹。不拖就打开，macOS 让它在一个临时的位置运行，应用会先提醒（见上面「本机的命令」）。
2. 双击打开。系统说 Apple 无法验证它是否含有恶意软件，只给「完成」和「移到废纸篓」。点「完成」。按住 Control 点「打开」的老办法在 macOS 15 上已经没有了。
3. 打开「系统设置 › 隐私与安全性」，往下翻，在说 Pneuma Base 被阻止的那一行点「仍要打开」，输入密码或用触控 ID。
4. 再双击一次，在弹出的对话框里点「仍要打开」。之后每次都直接打开。

另外：通知发不出去（系统拒绝本机签名的应用，见上面）；登录时打开不知道系统答不答应；只能在和构建的机器同一种芯片的 Mac 上运行，现在是 Apple 芯片。

用开发者证书签名并公证之后会变的：第一次打开只问一句「这是从互联网下载的，确定要打开吗」，不用去系统设置；通知和登录项按正常的应用对待。不会变的：没拖进「应用程序」就打开时照样在临时位置运行，那句提醒照样有用。要做的是：加入 Apple Developer Program 拿一张「Developer ID Application」证书；`build.sh` 里的两次 `codesign` 改用这张证书、加 `--options runtime` 和时间戳（Node 在加固的运行时里要 `com.apple.security.cs.allow-jit` 这个权限，nodejs.org 的 Node 自己的签名已经带着）；再用 `xcrun notarytool submit` 送去公证，`xcrun stapler staple` 把结果钉在应用上，最后打 zip。
