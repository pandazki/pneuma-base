# 各块先例俱在，却无人合而为一

**结论先行：没有找到任何一个产品或项目，同时做到下面四件事：（a）把读进来的资料和做出来的东西都当作一等条目放进同一个库；（b）把每样做出来的东西连回产生它的会话和它用到的资料；（c）不装软件也能读；（d）跨不同的 agent 产品。** CONTEXT.md 里“现有工具要么存记忆片段，要么存产出物，把读过的和做出来的放进同一个库、用来历连起来的不多”这个印象，经调研基本成立，收窄后的说法是：每一块都有人做，合起来没人做。离目标形状最近的是 Karpathy 的 LLM wiki 约定（raw、wiki、log 放在一个自描述文件夹里），但它没有机器可读的来历，也没有场景卡。来历、过期、文件夹格式、授权和插件这几个子问题，都有成熟的先例可借：W3C PROV 的词汇与 Pneuma 的“条目、场景、读、做”几乎一一对应；“可能过期”可以定义为构建系统里的“验证轨迹失败”（记下读取时的内容哈希，现在的哈希不同就算）；文件夹格式的共同做法是根目录声明文件加纯文本清单，索引可以重建；并发安全靠“每个文件只有一个写者、写完不再改”；授权在本机只能是约定加事后发现，真正的限制只在软件一侧；插件协议可以照 git-annex 的 special remote 来做。有一处需要改：CONTEXT.md 原则 5 的“一次会话读了 A 和 B、做出了 C，就粗略认为 C 来自 A 和 B”，恰好是 PROV 明确拒绝当作事实存的推断，应存成“读过”和“做出”两条事实，把“可能来自”留作派生视图。文中所有“未核实”和“缺口”的标记都照笔记原样保留，集中汇总见最后一节。

## 七家各得一块：读过的、做出的、会话三者没有合在一起

**记忆类产品存的是提炼后的片段，不是资料本身。** Claude Code 的 auto memory 每条记忆一个 Markdown 文件，frontmatter 只有 `type` 字段（user、feedback、project、reference），文档列出的字段里没有会话号或来源 ([Claude Code docs: memory](https://code.claude.com/docs/en/memory))。Claude 的 memory tool 是客户端文件操作，没有定义任何来历或会话元数据 ([Claude API docs: memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool))。Codex 的 memories 由后台从“符合条件的旧对话”生成，官方称之为“generated state”，页面没有说明记忆能否回链到源会话 ([OpenAI docs: Memories](https://learn.chatgpt.com/docs/customization/memories?surface=app))。Letta 的 MemFS 是带 git 版本的 Markdown 目录，唯一的来历是自由文本的 commit message ([Letta blog: Context Repositories](https://www.letta.com/blog/context-repositories))。这些文件库不装软件就能读，但读不出一条记忆来自哪次会话。2026 年的总趋势是“记忆变成一个 Markdown 文件夹”：Claude Code、Codex、Letta MemFS、OpenClaw、Basic Memory 都是如此，Claude Managed Agents 也把记忆库挂载成沙箱里的 `/mnt/memory/<slug>/` 目录 ([Claude docs: Managed Agents memory](https://platform.claude.com/docs/en/managed-agents/memory))。

**真有来源链接的系统，把链接锁在数据库或托管 API 里。** Graphiti/Zep 把原始 episode “byte-for-byte”保留，每条边带一个 `episodes` 列表记录哪些 episode 支撑了这条事实，但它不收 agent 的产出物，删除 episode 也不会重生成依赖它的摘要 ([Zep blog: provenance](https://www.getzep.com/blog/how-zep-tracks-provenance-in-agent-memory/))。Claude Managed Agents 的记忆每次修改都生成不可变版本，并“归属于会话”，但只存记忆文本，且是托管的 ([Claude docs: Managed Agents memory](https://platform.claude.com/docs/en/managed-agents/memory))。mem0 有按记忆 ID 的 ADD/UPDATE/DELETE 历史，一位评审者认为它的“从原始对话到提取事实”的来源很弱 ([Commonplace review of mem0](https://zby.github.io/commonplace/agent-memory-systems/reviews/mem0/))。Cognee 的 DataPoint 记录 `source_pipeline`、`source_task` 等字段，评审者称其为所评系统中最强的来历模型，但这条信息来自第三方代码评审，不是 Cognee 官方文档 ([Commonplace: Cognee](https://zby.github.io/commonplace/notes/related-systems/cognee))。

**产出物类产品知道产物属于谁，但不暴露它来自哪次对话、用了哪些输入。** Claude Code 的 artifact 发布到 claude.ai 账号下，`/artifacts` 能列出旧产物，但跨会话更新“必须给 Claude 它的 URL”，否则新会话会新建一个 ([Claude Code docs: artifacts](https://code.claude.com/docs/en/artifacts))。ChatGPT Library 把上传的和生成的文件放在同一个列表，可按“Uploaded or Generated”过滤，删除对话不删文件，但帮助文章没有记载“跳回来源对话”的入口，也没有记载生成文件与所用上传文件之间的链接 ([OpenAI help: Library for ChatGPT](https://help.openai.com/en/articles/20001052-library-for-chatgpt))。Manus 2.0 会把产物、上传附件和项目文件恢复到新沙箱，中间文件不恢复 ([Manus blog: Manus 2.0 sandbox](https://www.manus.im/blog/manus-sandbox))。Turso AgentFS 把文件和只追加的 `tool_calls` 表放在同一个 SQLite 文件里，但基础规范没有 `session_id`，文件行也不指向写它的工具调用，说明“放在一个库里”本身并不产生来历 ([AgentFS SPEC.md](https://github.com/tursodatabase/agentfs/blob/main/SPEC.md))。

**“产出物连回会话”只在 git 里的代码上出现。** Entire 的 checkpoint 存下关联的 commit、agent 会话、提示词与转录、工具活动和改动文件，放在仓库自己的 git ref 里，并用 `Entire-Checkpoint` trailer 把 commit 连回去，但只列改动的文件，只读过的文件不列 ([Entire docs: checkpoints](https://docs.entire.com/cli/checkpoints))。git-ai 用 `refs/notes/ai` 的 Authorship Log 把每行 AI 代码连到 agent、模型和提示词 ([git-ai: how it works](https://usegitai.com/docs/how-git-ai-works))。Cursor 起草的 Agent Trace 是厂商中立的 JSON 记录，把代码范围连到对话和贡献者，存储方式留给实现者；Thoughtworks Radar 2026 年 4 月把它放在“Assess” ([Thoughtworks Radar: Agent Trace](https://www.thoughtworks.com/radar/platforms/agent-trace))。这几个工具里，“读过的资料”只以转录文字的形式存在，不是被存下来的条目。

下表把调研结论压成一张能力矩阵。任何一行的成员都没有覆盖其他行，会话来历只出现在托管 API（Managed Agents）或绑定 git 的编码工具里（Entire、git-ai）。

| 能力 | 已有的做法 |
| --- | --- |
| 原始输入保留，派生内容链接到输入 | Graphiti/Zep；Cognee（第三方说法）；NotebookLM（引用跳回原文，[Google support](https://support.google.com/notebooklm/answer/16206563)） |
| 输入和输出并排列出 | ChatGPT Library、Manus、LLM-wiki 文件夹约定 |
| 产出连回产生它的会话 | Entire、git-ai、Agent Trace、SpecStory、Managed Agents 记忆版本 |
| 只追加的发生记录 | LLM-wiki 的 `log.md`、AgentFS `tool_calls`、OpenClaw 日记文件 |
| 不装软件也能读的普通文件夹 | Claude Code auto memory、Letta MemFS、Basic Memory、OpenClaw、SpecStory、LLM wiki |
| 跨 agent 产品通用 | Basic Memory 与 OpenMemory（MCP）、claude-mem 与 agent-memory（hooks）、git-ai、Entire；AGENTS.md 与 Agent Skills（只管说明） |

最接近目标形状的是 Karpathy 的 LLM wiki：原始来源“不可变”，wiki 由 LLM 拥有，一个 schema 文件（CLAUDE.md 或 AGENTS.md）定规矩，`log.md` 是“只追加的发生记录”，还有 lint 去查“被新来源取代的过期说法”。但那份 gist 没有描述任何把 wiki 页面连到原始来源的逐页机制，会话记录也只是日志行 ([Karpathy gist: LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f))。这正是 Pneuma Base 要补的那一格：格式上机器可读的来历，加场景卡。

用户抱怨的问题都指向同一处缺失，即条目缺少“从哪来、什么时候来”的链接。过期或自相矛盾的记忆会让 agent 给出“confident wrong action”（来自搜索摘要，归属于 HackerNoon 一文，未经抓取确认）；Cursor 在 2.1.x 有意移除了 Memories，Devin 和 Codex 也都建议把长期指引放进 Rules 或 AGENTS.md ([Cursor forum](https://forum.cursor.com/t/are-my-memories-gone/144057))；Claude Code 会在 `cleanupPeriodDays` 之后清理转录却保留记忆文件，记忆因此可能比它的来源会话活得更久，且不留回指 ([Claude Code docs: memory](https://code.claude.com/docs/en/memory))；Managed Agents 官方文档也直说，提示注入可以写进可读写的记忆库，“Later sessions then read that content as trusted memory”。这支持 CONTEXT.md 的立场：用户更信任朴素、可检查的文件，库的核心任务是记录来历并确定性地标出“可能过期”。

## 来历直接借 PROV，过期定义为验证轨迹失败

### PROV 给出现成的词汇，也指出一处该改的推断

W3C 的 PROV-DM 和 PROV-CONSTRAINTS 是 2013 年 4 月 30 日的 W3C Recommendation ([PROV-DM](https://www.w3.org/TR/prov-dm/))。它的核心词与 Pneuma 的词几乎一一对应：Entity 是条目，Activity 是场景，Agent 是 agent 或人，`used` 是读，`wasGeneratedBy` 是做。三个具体点值得借。第一，PROV 不允许一个 entity 改变状态，每个状态是一个独立 entity，用 `specializationOf` 连回持久的那个东西；落到 Pneuma，就是每个内容版本一个 entity，记录指向“当时读到的那个版本”。第二，一个场景用了 A 和 B 再生成 C，在 PROV 里“必要但不充分”于 C 派生自 A 和 B，`wasDerivedFrom` 是另一个更强的、“由未指明的方式确定”的声明 ([PROV-DM](https://www.w3.org/TR/prov-dm/))。CONTEXT.md 原则 5 的粗略推断正是 PROV 拒绝代替事实的那一种，建议改成：存 `used` 与 `wasGeneratedBy` 两类事实，“C 可能来自 A、B”作为派生视图展示，显式的 `wasDerivedFrom` 保留为可选的加强。第三，线索不需要新原语：PROV 的 Communication（`wasInformedBy`）定义的就是“场景 2 用了场景 1 生成的东西”；场景卡对应 Bundle，它本身是 entity，因此卡的作者也能记录 ([PROV-DM](https://www.w3.org/TR/prov-dm/))。（本条是笔记中的映射推断，不是 PROV 文本的直接结论。）

PROV 还提供了“来历不明”的几种说法：派生关系里的 activity、generation、usage 都是可选参数，`wasAttributedTo` 用于活动未知或无关的情形，规范化时用存在变量表示“确有其物但身份未知”，PROV 实例也“不必有效” ([PROV-CONSTRAINTS](https://www.w3.org/TR/prov-constraints/))。但没有任何标准把“来历不明”做成一等值，C2PA 的校验码 `ingredient.unknownProvenance` 和 `manifest.unknownProvenance` 只在规范的版本说明里见到，具体语义未核实。笔记据此建议把“不明”拆成三种互不相同的状态：未记录（文件出现或改变时没有对应场景，类似没有 run 记录的 DataLad commit）；已记录但可能不全（场景存在，读取清单是尽力而为，类似 SLSA 的 `resolvedDependencies`，其完整性“best effort, at least through SLSA Build L3”，[SLSA v1.1](https://slsa.dev/spec/v1.1/provenance)）；断言而非观察（agent 或人说的，不是库看到的，类似 C2PA 的 `gathered_assertions`，被携带但不由签署者担保，[C2PA 2.2](https://spec.c2pa.org/specifications/specifications/2.2/specs/C2PA_Specification.html)）。

### 自描述文件夹的来历先例：RO-Crate 与 Process Run Crate

RO-Crate 是离“自描述文件夹”最近的现有格式：根目录一个 `ro-crate-metadata.json`，根数据实体最少只需 `Dataset` 类型和一个 ISO 8601 的 `datePublished`，并且元数据“不一定列出或描述包里的所有文件” ([RO-Crate 1.2](https://www.researchobject.org/ro-crate/specification/1.2/root-data-entity.html))。这与“来历不明是正常状态”吻合：没被列出的文件不算错误。Process Run Crate 0.6 用 schema.org 的 `CreateAction` 描述一次“隐式工作流”：`instrument` 必须有，`object`（输入）可选，`result`（输出）推荐，`agent` 与 `endTime` 推荐，缺 `actionStatus` 时默认视为成功，几个 action 通过“一个的 result 是另一个的 object”串成工作流 ([Process Run Crate](https://www.researchobject.org/workflow-run-crate/profiles/process_run_crate/))。这与场景的形状相同：没有工作流定义，只有做了什么、读了什么、做出什么，适合作为场景卡的导出格式。CWLProv 走另一条路，用 BagIt 包存内容寻址的数据（SHA1）和 PROV 轨迹，能精确重放但占空间 ([CWLProv repo](https://github.com/common-workflow-language/cwlprov))；Pneuma “默认存引用、可选复制整段对话”落在两者之间。

### 读取怎么抓：声明式有盲区，macOS 上能依赖的只有 agent 这一层

数据与 ML 血缘工具多半靠声明。DVC 的 `deps`/`outs` 由用户写，文档只建议代码“Read/write exclusively from/to the specified dependencies and outputs”，没说明读了未声明文件会怎样 ([DVC dvc.yaml docs](https://doc.dvc.org/user-guide/project-structure/dvcyaml-files))；MLflow 有 `log_input` 却没有对应的输出表记录方法 ([Databricks KB](https://kb.databricks.com/machine-learning/lineage-for-the-output-table-with-predictions-is-not-tracked-in-mlflow-when-training-a-model))；W&B 的血缘边只来自 `use_artifact` 与 `log_artifact`，直接读本地文件没有边，但这一条仅有第三方教程支持，官方文档未核实。DataLad 在写入一侧是“观察式”的：`datalad run` 默认保存命令触发的所有改动，哪怕没声明 `outputs`，也挂到这次命令的 commit 上；没有任何改动就不写记录 ([datalad-run manual](https://docs.datalad.org/en/stable/generated/man/datalad-run.html))。Pneuma 可以借这个做法：场景里每个新增或变化的条目，不管有没有声明，都挂到该场景上。OpenLineage 把设计期声明（JobEvent）和运行期观察（RunEvent）分开，事件可以增量补充，这与“每个场景一个文件、只追加”相配 ([OpenLineage object model](https://openlineage.io/docs/spec/object-model))。

操作系统层面的读取抓取在 Linux 上成熟但昂贵：Grayson 等人 2024 年的基准里，几何平均的墙钟开销是 fsatrace 0%、CARE 45%、strace 66%、rr 146%、ReproZip 193%（列顺序取自提取出的表头，没有对照渲染后的表格核对），结论是“Current provenance collectors are too slow for 'always on'” ([Grayson et al. 2024](https://mir.cs.illinois.edu/marinov/publications/GraysonETAL24ProvenanceCollectorsSurvey.pdf))。macOS 更难：SIP 会让动态链接器忽略对受保护可执行文件（如 `/bin/sh`）的 `DYLD_INSERT_LIBRARIES`，fsatrace 需要关闭 SIP，Endpoint Security 需要受限的 Apple entitlement，ReproZip 只能在 Linux 上打包 ([Apple Developer Forums](https://developer.apple.com/forums/thread/731358)、[fsatrace](https://github.com/jacereda/fsatrace)、[ReproZip](https://reprozip.readthedocs.io/en/1.x/packing.html))。笔记没有找到 macOS 上读取捕获的基准，上面的数字都来自 Linux。该论文还指出，科学计算“可以接受一个能被不合作程序故意绕开、但多数时候有效的方案”，这与 CONTEXT.md 的“本机授权是约定”一致。实际可行的读取事件来源因此是 agent 这一层：它自己的文件读写与 shell 调用，类似 noWorkflow 对 Python 脚本的做法，shell 命令内部的读取看不到。笔记没有研究具体 agent 产品暴露哪些钩子（下文第四节单列了 Claude Code 的钩子字段）。可选的“复制读过的东西”可以借 Grayson 提出的 copy-on-write-after-read，只在源文件即将被改动前才复制。

### 可能过期：记下读取时的哈希，哈希变了就标出来

构建系统论文 Build Systems à la Carte（ICFP 2018）给出最干净的形式化说法：非输入键“最新”，当且仅当用任务描述和最终存储重新计算它，得到的值与存储里的完全一致 ([ICFP 2018 PDF](https://www.microsoft.com/en-us/research/wp-content/uploads/2018/03/build-systems.pdf))。真实系统用四种方式近似：脏位（Make 的时间戳、Excel）、验证轨迹（记录结果的哈希和读取过的依赖哈希，Shake、Ninja）、构造式轨迹（还存结果，Bazel、CloudBuild）、深构造式轨迹（只哈希终端输入，Nix、Buck）。Pneuma 无法重新计算，因为 agent 不是确定性函数，深构造式轨迹要求任务确定且放弃提前截断，不适用，只剩验证轨迹这个读法：一个做出来的条目版本是“可能过期”，当且仅当它所在场景记录的某个被读 entity，当前内容哈希与读取时记录的不同。这个检查是确定性的，不需要判断，符合“库只做确定性的事”。“可能”二字是准确的，因为库不能执行规范里的 `compute`。

由此可以得到四条具体的设计结论。第一，用内容哈希而不是时间戳：论文指出 Make 在备份软件、`touch`、时钟回退下会失灵，而这些正是 Dropbox 式同步插件会带来的情形。第二，传递性要标注：Excel 式的脏位会把所有传递依赖者标脏；验证轨迹只查直接依赖，并靠提前截断止住传播。Pneuma 从不重做东西，所以建议把直接过期作为事实显示，把“因上游可能过期而可能过期”作为单独的派生标记。第三，读取清单未知的条目，按论文的做法当作“依赖 RealWorld 的易变任务”，保守地一律视为可能过期。第四，Tup 的 `--ghosts` 记录“试图访问但不存在的文件”，对应一种负依赖：场景找过 X 没找到，之后 X 出现，场景的产物就可能过期 ([tup(1)](https://manpages.ubuntu.com/manpages/jammy/man1/tup.1.html))。笔记把 agent 会话类比为 Fabricate 式构建（有序脚本、OS 级读取、产出事先不声明），这是论文框架里唯一不能干净套用的模型。IPyflow 提供了“标出来、不重做”的交互先例：依赖的符号时间戳更新时高亮过时的 cell，响应式重跑是可选项 ([IPyflow dataflow model](https://ipyflow.readthedocs.io/en/latest/concepts/dataflow_model.html))；它能用时间戳，只因为它控制着单个内核里的时钟。

另一类可借的是 in-toto 与 SLSA 的“主体加谓词”形状：主体按摘要标识并假定不可变，谓词记录构建定义和运行详情 ([in-toto Statement v1](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md))。映射到 Pneuma：主体是做出来的条目版本（内容哈希），谓词是场景。按摘要标识能让记录在改名和同步后继续有效。签名不在范围内，但 SLSA 的告诫仍然适用：记录只和写它的一方一样可信，agent 写的场景卡是断言，不是观察 ([SLSA v1.1](https://slsa.dev/spec/v1.1/provenance))。C2PA 的三种 ingredient 角色（`parentOf`、`componentOf`、`inputTo`）可以作为加强“同场景”粗略关联的词汇：基于、嵌入、作为输入 ([CAI docs: ingredients](https://opensource.contentauthenticity.org/docs/manifest/writing/ingredients))，该页来自搜索摘要，C2PA 2.2 规范正文中 ingredient 部分笔记没有读完整。

## 文件夹即产品：根声明、身份写进树里、一个文件一个写者

### 自描述靠根目录声明文件和纯文本清单，索引一律可重建

只有档案类格式和 Maildir 是按“只有文件的读者也能看懂”设计的。OCFL 的存储根有 NAMASTE 声明文件 `0=ocfl_1.1`，并可用 `ocfl_layout.json` 记录路径布局规则，目标之一就是对象能在“没有原软件”的情况下被完全理解 ([OCFL 1.1 spec](https://ocfl.io/1.1/spec/))；BagIt（RFC 8493）要求 `bagit.txt` 和清单，载荷文件无需处理元数据即可访问 ([RFC 8493](https://www.rfc-editor.org/rfc/rfc8493))；Frictionless Data Package 要求顶层 `datapackage.json` ([datapackage.org](https://datapackage.org/standard/data-package/))。OCFL 的 `ocfl_layout.json` 是“根目录声明库怎么维护自己”最接近的先例。相反，Zotero、DEVONthink、Apple Photos 把数据库或不公开的布局放在中心，并警告用户不要碰。DEVONthink 和 Photos 的这类说法来自论坛和社区帖，属于二手或轶事，不是官方说明。Eagle 的 `.library` 官方只承认“不能被其他软件灵活访问”，其内部布局只有反向工程的第三方描述，未核实。

“记录是本体，索引是缓存”也有强先例。Fossil 说元数据“contains no new information”，整个元数据可由 `fossil rebuild` 重算 ([Fossil technical overview](https://fossil-scm.org/home/doc/trunk/www/tech_overview.wiki))；Perkeep 说“you can lose your index at any time” ([Perkeep overview](https://perkeep.org/doc/overview))；Zotero 不备份 `fulltext.sqlite`，因为能重建 ([Zotero: data directory](https://www.zotero.org/support/zotero_data))。

### 身份：哈希管“是不是同一份字节”，编辑后仍不变的身份必须自己发，并写进文件树

没有一个被调研的系统靠文件系统本身得到稳定身份。git 不记录改名，靠相似度推断（默认 50%，穷举配对为 O(N²)，受 `diff.renameLimit`（当前 1000）限制，[git-diff](https://git-scm.com/docs/git-diff)）；git-annex 和 OCFL 用内容哈希，搬家安全但每次编辑都变，git-annex 的 `SHA256E` 键还带扩展名，笔记引用的一条用户评论称 `.jpg` 与 `.JPG` 会产生不同的键 ([git-annex backends](https://git-annex.branchable.com/backends/))。所有“可编辑且身份保持”的系统都发 ID：Perkeep 的 permanode“is really just a signed random number”，状态由依序应用的 claim 得到 ([Perkeep permanode](https://perkeep.org/doc/schema/permanode))；Zotero 的 8 位文件夹名、Eagle 的 `<ITEM_ID>.info` 文件夹（后者来自第三方，未核实）。Obsidian 只在 app 内改名时更新链接，外部改名表现为删除加新建，关闭期间的移动不会被修复 ([External Rename Handler](https://community.obsidian.md/plugins/external-rename-handler)、[Obsidian forum](https://forum.obsidian.md/t/auto-update-links-for-files-moved-while-obsidian-is-closed/91670))。

笔记的推断是：被发的 ID 必须写在文件树里，放进文件夹名、sidecar、frontmatter 或清单，不能只在数据库里，否则人手工搬动或同步后就丢了。手工复制文件夹会连 ID 一起复制，所以要能发现重复。这条推断没有来源直接覆盖复制重复的情形。反过来，xattr、inode、书签都不可靠：Dropbox 只同步固定清单里的 xattr；iCloud Drive 默认剥离 xattr，只有名字以 `#S` 结尾的自定义属性能保留，每项上限约 32 KiB ([Eclectic Light 2024](https://eclecticlight.co/2024/09/13/from-quarantine-to-provenance-how-xattrs-are-copied/))；Syncthing 的 xattr 同步默认关闭 ([Syncthing: syncXattrs](https://docs.syncthing.net/advanced/folder-sync-xattrs))；苹果文档明说文件引用 URL“should never be persistently stored” ([Apple: NSURL](https://developer.apple.com/library/archive/documentation/cocoa/Conceptual/LowLevelFileMgmt/Articles/FileManagementNSURL.html))，该条来自搜索摘要。

### 元数据放哪里：按条目形态分流，目录型条目要有标记文件

frontmatter 只适用于能容纳头部的文本，Obsidian 的属性是 YAML 且只支持扁平、固定类型，嵌套“not currently supported” ([Obsidian: Properties](https://obsidian.md/help/properties))。二进制文件和目录型条目（一个网站、一个代码项目）需要 sidecar、每条一个文件夹或清单。每单元一份清单（BagIt、OCFL）避免了载荷与元数据分家，但清单成为所有写者共改的单点；git-annex 给出第三条路：按稳定 key 把元数据分片成许多小的只追加日志，带时间戳记录增和删，所以“旧行不会把已删除的值再加回来” ([git-annex internals](https://git-annex.branchable.com/internals/))。目录型条目的所有先例都用根部标记文件，OCFL 的 `0=ocfl_object_1.1`、BagIt 的 `bagit.txt`、git 的 `160000` gitlink、Apple 包的扩展名；OCFL 规定存储层级“MUST be terminated by OCFL Object Roots”。没有标记，扫描外部改动时就会钻进 `node_modules` 或 `.git` 把里面每个文件都当成库内容。笔记也没有找到量化“sidecar 对数据库”在 10 万条目规模下优劣的来源，这部分权衡是推断。

### 并发与同步：同步工具只认“同一路径两边都改了”，所以每个文件只能有一个写者

Syncthing、Dropbox、rclone bisync 都把冲突定义为同一路径在两侧都有改动，冲突文件被改名保留并继续被当作普通文件传播，没有任何一个会合并内容 ([Syncthing: understanding synchronization](https://docs.syncthing.net/users/syncing.html)、[Dropbox: conflicted copy](https://help.dropbox.com/organize/conflicted-copy)、[rclone bisync](https://rclone.org/bisync/))。所以“文件内追加”本身不够：两台机器往同一个文件追加仍然冲突。真正不会产生冲突的是每次写入都创建新的、名字唯一的文件：Maildir 先写 `tmp/` 再原子重命名到 `new/`，设计目标就是消除文件锁（笔记引用的是维基百科，Bernstein 原页抓取失败，属二手）；Jujutsu 的操作头是以操作 ID 命名的空文件，“Writing the new file is what makes the operation visible” ([jj concurrency](https://docs.jj-vcs.dev/latest/technical/concurrency/))；automerge-repo 的增量块以变更字节的哈希命名，同名必同内容，压缩时只删自己加载过的块，因为“another process might have written new changes since it started” ([Automerge: storage](https://automerge.org/docs/reference/under-the-hood/storage/))。这与“每个场景一个文件、只追加”的原则吻合，要严格成立，每个场景文件必须由恰好一个写者写。剩下的隐患是删除与压缩同添加的竞争、任何单一的“当前”指针文件、以及同步中途读到写一半的文件。

最大的反例是把单个可变存储放进同步目录：gitfaq 写明“It is important not to use a cloud syncing service to sync any portion of a Git repository” ([gitfaq](https://git-scm.com/docs/gitfaq))；SQLite 在事务中途被复制，或与 `-wal` 分离时会损坏 ([SQLite: How To Corrupt](https://www.sqlite.org/howtocorrupt.html))；Zotero 说放进云盘“is extremely likely to corrupt your database” ([Zotero KB](https://www.zotero.org/support/kb/data_directory_in_cloud_storage_folder))。连专为此设计的 jj 也承认用 Dropbox 或 rsync 时有已知问题。结论有两条：查看器的 SQLite 索引要放在被同步的文件夹之外，或设为忽略并可重建；条目若自带 `.git`，要把它排除在文件同步之外或交给 git 自己同步。

### 扫描外部改动：先 stat 后哈希，事件只是提示

笔记里这一小节有一组在一台 Apple 芯片的 Mac 上的实测数据（热缓存，10 万个 4 KiB 文件，1000 个目录），没有公开网址，只有笔记中记录的脚本：`os.scandir` 加每个文件 `lstat` 约 0.23–0.25 秒，`git status --porcelain` 约 0.18–0.22 秒，读取并 SHA-256 全部文件（410 MB）3.35 秒。冷缓存、机械盘、网络盘和 iCloud 占位文件没有测。含义是：约 10 万文件的库在本地 SSD 上做一次全量元数据扫描很便宜，启动时和定期全扫可以承受，哈希约贵 15 倍且随字节数增长，所以快照缓存应记录 (size, mtime, inode, hash)，仅在 size 或 mtime 变化时才重哈希，这是 git、Syncthing 和 Unison 的共同做法 ([Syncthing: syncing](https://docs.syncthing.net/users/syncing.html)、[Unison manual](https://raw.githubusercontent.com/bcpierce00/unison/documentation/unison-manual.html))。文件事件只是加速：Watchman 在事件队列溢出时会“assume that all the files have been modified”并重新爬整棵树 ([Watchman install docs](https://meta.github.io/watchman/docs/install))，git 的 FSMonitor 令牌不匹配时同样退回全扫 ([GitHub blog: FSMonitor](https://github.blog/engineering/improve-git-monorepo-performance-with-a-file-system-monitor/))，正确性不能依赖事件。消失的路径加上同哈希的新路径可判为搬家，这是 git 的精确改名情形。

### 手写与 agent 写的记录格式：一行一条，开头固定，不依赖顺序，坏行要报错

可靠解析的格式有三个共同点：一行一条记录，行首有固定标记或日期，不依赖顺序。beancount 解析后会重新按日期排序；todo.txt 一行一个任务；JSON Lines 每行一个 JSON 值，拼接文件也成立 ([beancount](https://beancount.github.io/docs/beancount_language_syntax/)、[todo.txt](https://github.com/todotxt/todo.txt)、[jsonlines.org](https://jsonlines.org/))。陷阱有三个：YAML 1.1 把未加引号的 `NO`、`on` 等解析成布尔（“Norway problem”，来源是博客与二手文章，没有取到 YAML 规范原文，[bram.us](https://bram.us/2022/01/11/yaml-the-norway-problem)）；Org-mode 的解析依赖每个文档各自的配置；beancount 对不合法的行“silently ignored”。最后一条，笔记给出的推荐（非有来源的事实）是记录解析器应当报告不可解析行的文件和行号，与 beancount 的选择相反。路径需要转义规则，并要表态如何处理大小写和 Unicode 规范化，BagIt 就规定了换行和 `%` 的百分号编码 ([RFC 8493](https://www.rfc-editor.org/rfc/rfc8493))。

## 授权在本机是约定，发现靠用户级文件，插件协议抄 git-annex

### 授权的形状可抄 UCAN 与 Biscuit，但本机上没有验证者

令牌式能力系统共享同一种授权形状：签发者、受众、主体或资源、命令、条件、不早于与过期时间、唯一标识；持有者只能在链上追加，只能收窄不能放宽。UCAN v1.0.0 的载荷字段是 `iss`、`aud`、`sub`、`cmd`、`args`、`nonce`、`meta`、`nbf`、`exp`，规定“Each direct delegation MUST either directly restate or attenuate (diminish) its capabilities” ([UCAN spec](https://github.com/ucan-wg/spec))。Biscuit 的块链用 Datalog 写权限和检查，过期只是一条检查，验证方（authorizer）加入请求上下文并以自己的策略为准，任何知道根公钥的系统都能离线验证 ([Biscuit spec](https://doc.biscuitsec.org/reference/specifications))。吊销一律要靠验证方查吊销清单：UCAN 称吊销是“a last resort”，因为“UCANs do not offer confinement”。S3 预签名 URL 是最简授权，“Creating a presigned URL happens locally, so Amazon S3 doesn't generate an issuance event”，AWS 要求签发方自己记录用户、签名会话、桶、键、操作和过期时间 ([AWS S3 presigned URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html))。对应到库：每次授权的签发都应写进库自己的管理日志。

在本机，没有任何验证者夹在 agent 和文件之间，令牌执行不了任何限制，只能当作一份可核对的意图声明，供事后检查拿写入去比对。这与 CONTEXT.md 的 2.10 和原则 8 一致，而且业界的编码 agent 自己也这么认。Claude Code 文档明说，Read/Edit 的 deny 规则不适用于“arbitrary subprocesses that read or write files indirectly, like a Python or Node script”；它的沙箱默认关闭，只管 shell 命令，且“Most of the machine”可读，包括 `~/.ssh`；并且 `denyRead` 不拦 Read 工具 ([Claude Code permissions](https://code.claude.com/docs/en/permissions)、[Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing))。Codex 的 `workspace-write` 是默认模式，沙箱作用于派生命令，不止内置文件操作 ([Codex sandboxing](https://learn.chatgpt.com/docs/sandboxing))；OpenCode 没有操作系统沙箱，“`shell` runs with the host user's filesystem, process, and network authority” ([OpenCode permissions](https://opencode.ai/docs/permissions/))。Gemini CLI 要用 `--sandbox`、`GEMINI_SANDBOX` 或设置启用，页面没有写默认值。给 agent 授予库目录，每个工具都有原生的“额外目录”设置，但格式互不相同：Claude 的 `additionalDirectories` 或 `--add-dir`（后者还会加载该目录里的 `.claude/skills/`），Codex 的权限配置里的 workspace roots，Gemini 的 `includeDirectories`，OpenCode 的 `external_directory`。要把 agent 限制在一个区域，还要同时写其他区域的 deny 规则和沙箱设置。这里面 Gemini 的信任文件夹一条仅来自搜索摘要。

Codex 的权限配置允许“deny > write > read”的路径规则和 deny-read 通配符，扩展 `:workspace` 时 `.git`、`.agents`、`.codex`、`.aws` 默认只读 ([Codex permissions](https://learn.chatgpt.com/docs/permissions))；与此对照，CODEOWNERS 展示的模式是“按路径的所有者加默认只是建议，除非开启门禁”，可对应到“区域即子文件夹、本机建议、经软件才强制”。

### 会话号：能用，但没有一个是稳妥的公开约定

来历要靠 CLI 知道自己在哪次会话里被调用。Claude Code 的钩子文档明确提供 `session_id` 和 `transcript_path` ([Claude Code hooks](https://code.claude.com/docs/en/hooks))。笔记在 Claude Code v2.1.331 上观察到，agent 运行的 Bash 命令环境里有 `CLAUDECODE=1` 和 `CLAUDE_CODE_SESSION_ID=<uuid>`，转录文件名正是这个 uuid；但钩子文档没有记载这个环境变量，所以它是观察到、未文档化的。Codex 把会话写成 `~/.codex/sessions/YYYY/MM/DD/rollout-<timestamp>-<uuid>.jsonl`，二进制里有 `CODEX_THREAD_ID` 等字符串，但没有验证它们是否真的注入命令环境（未核实），官方环境变量页只列 Codex 读取的变量 ([Codex env vars](https://learn.chatgpt.com/docs/config-file/environment-variables))；Gemini 的会话按项目哈希存放，没有公开环境变量 ([Gemini CLI session management](https://geminicli.com/docs/cli/session-management))；OpenCode 与 Cursor 的会话存放和环境变量没有研究。稳妥的做法是：接受显式的 `--session` 参数或环境变量，其次嗅探已知变量，其余记为“会话未知”。MCP 2026-07-28 的方向也一致：协议级会话和 `Mcp-Session-Id` 被删除，“Servers that need cross-call state use explicit, server-minted handles passed as ordinary tool arguments”，应把会话或场景 ID 当作普通参数传 ([MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog))。

### MCP 不能再靠 Roots 限定区域

2026-07-28 版 MCP 已无状态，没有 `initialize` 握手，Roots、Sampling、Logging 被弃用，建议改用工具参数、资源 URI 或服务器配置传目录 ([MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog))。授权是可选的，仅适用于 HTTP 传输，stdio 服务器“SHOULD NOT”照此规范，而是从环境取凭据；HTTP 令牌要用 RFC 8707 的 `resource` 参数绑定受众，缺 scope 时返回 403 `insufficient_scope` 并做 step-up ([MCP Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization))。所以“只暴露库的一个区域”的 MCP 服务器，要靠自己的启动配置（stdio，如带区域和授权参数）或令牌 scope 加受众（HTTP）来限定，不能指望客户端声明的 roots。笔记也指出，Resources 页面本身、Skills over MCP 扩展、Claude Code 与 Codex 在用户级注册 MCP 服务器的方式，这次没有重新核实。

### 发现：没有任何东西会向任意 agent 自报家门

一个在别的目录、别的产品里的 agent，要发现库的存在，几乎总是走四条路之一：与工作目录或 git 仓库绑定的路径、产品自己的主目录、每个客户端各自的配置（MCP、hooks、skill 目录）、托管账号的列表。Claude Code 的 auto memory 以 git 仓库为键，换仓库就换记忆 ([Claude Code docs: memory](https://code.claude.com/docs/en/memory))；Managed Agents 创建会话时挂载记忆库，并在系统提示里自动加一段说明挂载位置 ([Claude docs: Managed Agents memory](https://platform.claude.com/docs/en/managed-agents/memory))；基于 MCP 的存储要在每个客户端分别配置。一个已装好的 hooks 方案（claude-mem 支持十几种 agent）说明跨产品装钩子可行，但得逐产品装 ([claude-mem repo](https://github.com/thedotmack/claude-mem))。笔记没有端到端测过第二个产品的发现路径，以上都来自文档。

跨产品、零服务器的那一层是指令与技能的 Markdown。Agent Skills 是开放标准：一个含 `SKILL.md` 的目录，必填 `name`（不超过 64 字符，必须与父目录同名）和 `description`（不超过 1024 字符），启动时只加载约 100 token 的元数据，用到时才加载正文 ([Agent Skills spec](https://agentskills.io/specification))。Claude Code 读 `~/.claude/skills` 与 `.claude/skills`，Codex 读 `~/.agents/skills` 与 `.agents/skills`，并明说支持符号链接 skill 文件夹 ([Claude Code skills](https://code.claude.com/docs/en/skills)、[Codex skills](https://learn.chatgpt.com/docs/build-skills))；Claude Code 对符号链接 skill 目录的处理没有核实。指令文件也不统一：Claude 读 CLAUDE.md，只有目录里没有 CLAUDE.md 时才读 AGENTS.md，用户级的 `~/.claude/CLAUDE.md` 不计入这个判断；Codex 读 `~/.codex/AGENTS.md` 加项目文件，合计上限 32 KiB ([Claude Code docs: memory](https://code.claude.com/docs/en/memory)、[Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md))。描述会被截断：Claude 在技能列表中把 `description` 加 `when_to_use` 截到 1,536 字符，Codex 整个列表限制在上下文的 2%（未知时 8,000 字符）。落到“一键生成技能和授权”上：在库里放一份只用标准字段的 canonical `SKILL.md`，描述开头就写触发条件，再给每个 agent 装指针（符号链接或复制到各自的 skills 目录，目录名必须等于 `name`）；备选是用户级指令里的一行引用，如 `~/.claude/CLAUDE.md` 里的 `@/abs/path`，它每次会话都加载，占用上下文，而技能在激活前只占约 100 token。Gemini、Cursor、OpenCode 是否读 `.agents/skills`，笔记没有核实。

### 事后检查的呈现方式，和插件契约

“只靠约定，事后发现”的成熟系统有四个共同点：基线不能被被审计方悄悄改写，按需比对，违规在正常界面里列出，系统自己拿不准时锁住自动动作而不是猜。AIDE 创建摘要数据库再做校验，记录摘要、类型、权限、inode、属主、大小、各种时间 ([AIDE](https://aide.github.io/))；CODEOWNERS 的违规显示在文件视图并可通过 API 读取，“invalid syntax”的行被跳过 ([GitHub CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners))；Rekor 要求日志保持只追加 ([Sigstore Rekor overview](https://docs.sigstore.dev/logging/overview/))。“来历不明”和“可能过期”就是 AIDE 式的完整性扫描：每条目的哈希与大小或时间，对照记录，输出新增、消失、无记录改变的清单。AIDE 自己的工作流和“基线放只读介质”的建议，笔记没有从抓到的页面核实。因为库的记录对 agent 可写，每场景一个、只追加的文件，加可选的哈希链（Rekor 式），只能让悄悄改写可被发现，不能让它不可能。

部署与同步插件的契约，git remote helper 和 git-annex 的外部 special remote 给出了稳定的模式：PATH 上按命名约定找到的可执行文件（`git-remote-<x>`、`git-annex-remote-<x>`），按行的 stdin/stdout 协议，先握手声明能力，必需动词很少，可选动词回 `UNSUPPORTED`，并且插件的少量状态放在仓库自己里面，随文件夹走 ([gitremote-helpers](https://git-scm.com/docs/gitremote-helpers)、[git-annex external special remote protocol](https://git-annex.branchable.com/design/external_special_remote_protocol/))。git-annex 的 `CHECKPRESENT` 返回 SUCCESS、FAILURE 或 UNKNOWN 三态，`INITREMOTE` 要求幂等，`WHEREIS` 应当不碰网络。笔记推断出的 Pneuma 版本是：`pneuma-base-plugin-<name>`，能力握手在先，必需 `PREPARE`、`PUSH item`、`STATUS item`（有、无、未知）、`REMOVE item`，可选 `LIST`、`COST`、`INFO`。“100 个网站只部署 40 个”映射到三份状态，沿用 Terraform 和 Kubernetes 的分法：期望状态是库里每个条目的声明（可部署能力加开关），上次已知的实际状态是库里按插件命名空间存的记录（部署地址、内容哈希、时间），真相在远端，由刷新去核对；Terraform 要求每个远端对象只绑定一个资源实例，“关掉”才能安全删除 ([Terraform state purpose](https://developer.hashicorp.com/terraform/language/state/purpose)、[Kubernetes controllers](https://kubernetes.io/docs/concepts/architecture/controller/))。Cloudflare 一侧，Pages 已被带静态资源的 Workers 取代，用 `wrangler deploy` 并以 `assets.directory` 指向文件 ([Cloudflare: migrate from Pages](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/))，对部署插件的目标有直接意义。

“插件只认能力，不认具体类型”有强先例：LSP 约定“Clients should ignore server capabilities they don't understand”，缺失属性视为没有该能力 ([LSP 3.17](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/))；git 把 `*` 前缀的未知必需能力定为致命错误；Kubernetes 标签“do not directly imply semantics to the core system”，且 ReplicaSet 的选择器不得重叠 ([Kubernetes labels](https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/))。声明如何保持诚实：Nix 在求值期就拒绝 `meta.broken` 或平台不符的包 ([Nixpkgs manual](https://nixos.org/manual/nixpkgs/stable/#chap-meta))。对应的格式规则是：未知的能力键忽略，缺键即无，必须理解的能力打标记，读者不理解就拒绝操作；部署插件在计划阶段检查必需字段（输出目录、入口文件）并列出拒绝原因；两个部署目标不应悄悄认领同一个条目。

双向同步插件对格式的要求，是本调研最实用的一条：同步工具不合并内容，所以格式必须保证每个文件一个写者（文件名带会话号和设备），关闭后的记录文件不再修改（更正写新文件），写入走临时名加重命名且临时名在忽略清单上，派生索引放在排除路径里，扫描器能把 `.sync-conflict-`、“conflicted copy”之类的名字识别为需要人或 agent 决定的项，库根放一个哨兵文件让同步插件在面对空目录或错误目录时拒绝运行。rclone bisync 提供了可抄的护栏：`--check-access` 哨兵、`--max-delete` 默认 50% 超过即中止、锁文件、严重错误后的锁定 ([rclone bisync](https://rclone.org/bisync/))。条目内容本身（如两个 agent 改同一个产物）仍可能冲突，那正是可选的“有版本”能力的用武之地。

## 笔记里仍未核实的事项和缺口

这里把笔记标出的“未核实”和“缺口”汇总，不要把它们当作已确认的事实。其一，产品层面：没有核对 ChatGPT 消费版记忆的官方文档，也不清楚 claude.ai 产物库或 ChatGPT Library 的界面是否有“来源对话”链接；Basic Memory 的笔记是否带会话或来源字段未确认；Devin 的会话与产物文档、Cursor 后台 agent 产物、v0 项目历史、Replit Agent、Factory 的追溯能力没有查；学术或个人数据仓库类项目（如 Solid pod、基于 PROV 的工具）与 agent 工作区的结合没有查；Cognee 当前的存储和来历结构来自第三方评审；Codex 是否读取能指向库外存储的全局 `~/.codex/AGENTS.md` 只是笔记作者的记忆，未核实；agentskills.io 规范文本本身没有直接读，事实来自 Codex 文档与 Anthropic 公告；各种发现路径都没有用第二个产品端到端测试过。

其二，来历与过期：没有读 PROV-O 的 OWL 编码，也没有核实 PROV-CONSTRAINTS 中从生成与使用推出 `wasInformedBy` 的那条推理是否存在；C2PA 的 ingredient 部分没有通读，`unknownProvenance` 的确切语义未核实，SLSA v1.2 页面没有读；W&B 对未声明读取的行为只有第三方教程；Build Systems à la Carte 只读了 ICFP 2018 版，没有核对 2020 年 JFP 版，Shake、Pluto、redo 的位置只来自这篇论文；macOS 上没有读取捕获的基准，eBPF 的数字来自一篇同行评审状态未确认的 2026 年 arXiv 研究；是否有 agent 产品暴露可记录读取的钩子，笔记没有系统研究。

其三，文件夹格式：Jujutsu 的操作对象编码、Perkeep 的本地块存储布局、官方的 Eagle 与 DEVONthink 包规范都没有核实；zip 里 xattr 的行为、iCloud 或 Dropbox 下载是否保留 inode 与创建时间、iCloud 冲突命名都没有找到一手来源；冷缓存、机械盘和网络盘的扫描开销没有测，FSEvents 的合并与历史重放没有研究；没有来源量化 sidecar 对数据库的权衡，也没有比较各格式的解析错误率。

其四，授权与插件：Codex 是否真的把 `CODEX_THREAD_ID`、`CODEX_SESSION_ID` 注入命令环境未验证；OpenCode 与 Cursor 的会话存放和环境变量未研究；Claude Code 对符号链接 skill 目录的处理、Gemini 与 Cursor 与 OpenCode 的 skills 目录未核实；UCAN 的 Delegation、Invocation、Revocation 子规范、经典对象能力文献、Biscuit 与 UCAN 库在 2026 年 11 月是否仍在维护、AIDE 的完整工作流、git hooks、Certificate Transparency 都没有取到；rclone backend 接口、Terraform 的 gRPC 插件协议、Vercel 与 Netlify 的部署模型、npm `scripts` 都没有抓取。

## 结语

这次调研把“有没有现成的”拆开看，答案有些反直觉：缺的不是任何一块技术，而是一个约束。几乎每个现成系统要么把来历锁在数据库或托管 API 里，要么只覆盖 git 里的代码，要么干脆没有来历；而可读的纯文件夹约定（LLM wiki、Obsidian 保险库、AGENTS.md 与 Skills）又都不规定来历怎么记。Pneuma Base 的差异化空间因此很具体：在一个 BagIt 或 OCFL 式的、根部有声明文件的文件夹里，把 PROV 的 `used` 与 `wasGeneratedBy` 写成每场景一个、只追加、单写者的纯文本文件，条目按内容哈希版本化、按自己发的 ID 识别，“可能过期”则是对这些记录做的一次确定性哈希比对。

调研也迫使几条设计表述变得更精确。“来历”应拆成观察到的、断言的、未记录的三种；“读过”必须是一个带哈希的具体版本；原则 5 的粗略派生应降级为视图；会话号不能指望 agent 产品替你提供，只能是显式参数加尽力嗅探；本机授权的诚实说法是“一份可核对的意图声明”，连 Claude Code 自己的文档也这么说它的规则。最大的未验证风险在读取这一侧：macOS 上没有廉价、无需特权的读取捕获，所有声明式血缘工具都有同样的盲区，所以“读取清单是尽力而为”要作为格式里的一等事实写出来，而不是当成实现细节。
