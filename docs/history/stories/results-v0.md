# 用户故事过模型 v0 的结果

2026-11-25。79 条故事（`everyday.md` 39 条，`adversarial.md` 40 条）由没看过模型的子代理只凭 `CONTEXT.md` 写成。逐条过模型这一步是我自己做的。

对象是 `MODEL.md` 的 v0。下面的修改都还是建议，没有写回 `MODEL.md`。

## 1. 总的结果

| 结果 | 条数 | 意思 |
| --- | --- | --- |
| 答上 | 19 | v0 原样给出确定的答案 |
| 要补 | 49 | 框架装得下，但缺一个概念、一种事实或一个状态 |
| 答错 | 6 | v0 给出确定的答案，但答案不对 |
| 没定 | 5 | 靠模型定不了，要你定或等调研 |

顺利的故事里答上的占一半（39 条里 18 条）。出错和边界的故事里只有 1 条原样答上（40 条里 1 条），这在预期之内，它们就是为这个写的。

**没有被压垮的部分：**「库 = (F, E)，视图是确定函数」「条目和快照分开」「对不上的情形都有名字」。79 条里没有一条要求放弃这三点，其中第三点被用得最多。

**被压得最重的部分：** 场景的定义、线索的定义、过期的定义、两份记录合并时的规则。

## 3. 压出来的修改

按主题分组。括号里是压出它的故事，“日”是日常，“对”是对抗。

### 场景

1. **场景不属于一个行动者。** 行动者挂在每条事实上。事实另有一栏“归于”：agent 替人记下“这两篇是她带进来的”时，记的是 agent，归于人。（日 2、3、4、22、28；对 9）
2. **人不经 agent 做的事也是场景。** 边界是工具的一次使用，可以没有“要解决什么”。（日 17、22、23、24；对 28）
3. **开场要记工作目录和机器；场景可以有上级场景。** 子代理记的场景指向主会话的场景。（日 12、29；对 9）
4. **场景可以分段。** 行动者可以记一条“另起一段，要解决的是……”，粗略来历只在段内算。默认一段。这条我拿不准，见第 5 节。（对 8）
5. **对话有三种留法。** 只留引用；复制一份作场景的附件；两者都有。副本是某一刻的，可以有多份。引用有三种情况：还在、失效、这台机器上查不了。引用失效和可能过期不是一回事。（日 13；对 10、38）

### 条目

6. **条目上可以有备注。** 人写的“1962 年，外婆家门口”跟着条目走。（日 22、23）
7. **目录条目拥有它下面的全部文件，条目不嵌套。** 读和来自可以细到目录条目里的一个文件。只读了 `index.html` 的审阅稿，不因为别的样式文件改了而过期。（日 20、25；对 17）
8. **引用形体是库里的一张描述卡。** 卡上写着东西在哪、多大、怎么取。外面的东西变没变，靠观测事实。（日 17、21；对 18）
9. **版本就是被记下的快照。** 没声明有版本的条目，旧内容不留，只留指纹历史。（日 11、20、28；对 2、23）
10. **媒体类型由文件算出，是视图。**（日 35）

### 事实

11. **读的对象可以是库外的东西。** 只留一句描述，不是条目，没有身份，不参与过期。读另一个库里的条目是它的一种，带库标识和条目号。所以库要有标识。（对 4、5、7）
12. **读带“读的时间”。** agent 10:00 读、11:00 才记，中间别人改过，快照按 10:00 的记录解析。（对 11）
13. **改带“基于哪个快照”。** 它和记录里的上一个快照对不上，就是盖掉了没见过的改动，视图把它标出来。（对 6、11、23）
14. **观测也是事实。** 工具机械记下的指纹、外部资料的状态、远端的状态。上一次的指纹必须在记录里，不能只在索引里，否则删掉索引就发现不了改动。（对 18、29、40）
15. **更正引用被更正的那条事实。** 两条都留着，视图用最新的。（对 32）
16. **每条事实带“怎么知道的”。** 自报、手写、工具经手、从会话记录提取。精确的来自是常规做法，粗略的是兜底，视图标出每条关系的等级。（日 2、8、9、18；对 4、32）

### 过期

17. **来源不在和来源已变分开。** 只有后者叫可能过期。前者是“查不到原件”。（对 12、16、20、35）
18. **改继承上一个快照的来自。** 这次读了同一个来源的新快照，才替换掉旧的。内容没变但对照了新上游，记成复核。上游重做后内容相同，下游的标记自动消失。（对 19；日 11）
19. **小改。** 改动的人可以声明“这次改动不影响下游”，下游不标。错别字和规则改动的区别由人或 agent 判断，库只记这个声明。（对 22）
20. **接替。** “Y 接替了 X”是一条事实。用在新版本换了文件名进来、一份拆成两份、两份合成一份、重做成了新文件。X 的下游标成“来源有了后继”。（对 16、21；日 11）

### 身份和对不上的情形

21. **另立。** 默认同一个路径就是同一个条目。在访达里点了“替换”、换成了另一个客户的文件，由人或 agent 事后声明“从这个快照起是另一样东西”。在此之前下游被标成可能过期，这个信号是对的。（对 2、15）
22. **入册撞上已有条目的路径时，后到的条目号是先有的别名。** 同一秒两个 agent 存同一个文件、同步时记录比文件晚到，都落在这里。（对 11、13）
23. **新状态“分叉”。** 同一个条目的两个快照出现在两个路径上。两台机器离线各改各的，同步后就是这样。（对 12、13）
24. **新状态“待指认”。** 指纹相同的不止一对，不能确定谁搬到了哪。（对 3、14）
25. **“失踪”改叫“不在”。** 被删了、还没同步到、只拷了一半，本机上分不出来，不该用带判断的词。（对 13、20、35）
26. **记录自己的对不上也要有名字。** 指不到东西的事实；被引用却找不到入册的条目号，后者说明有记录丢了。（对 32、33）

### 线索

27. **线索是两种视图。**
    - 一样东西的来龙去脉：沿“来自”往上、往下。
    - 一个范围内场景的分组：一个场景用了另一个场景放进来或改过的东西，就连起来。
28. **条目可以声明“公用”。** 风格指南、待办清单这类东西不拿来连线索。库可以列出被很多场景用过的条目，是否公用由人或 agent 声明。（日 5、6、15、38；对 8、14、22、23、39）

写故事的子代理自己在这里矛盾了：日常 6 说综述和基金申请“连成一条线索”，日常 38 说它们是三条。人心里的“一件事”不是图上的连通块。库给出图和分组，起名字、定哪些算一件事是人或 agent 的事（日常 15 里正是 Claude Code 给线索起的名）。

### 区域、授权、库

29. **视图按看得见的范围算。** 事实引用别的条目时只写号。看不到的显示成“另有 N 项不可见”，查找搜不到，线索在那里断开。（对 24、27）
30. **区域是路径。** 文件夹被整理没了，区域就空了，授权不再覆盖任何文件。这是有名字的状态，库列出来。（对 3）
31. **分出。** 把一个区域做成单独的库是一个操作，两边的管理日志各记一条。条目的身份是库标识加条目号，分出去以后各走各的。（对 26）
32. **授权也发给人。** 没带授权的事实照样记，行动者标成“自称”。（日 31、37）

### 部署

33. **实况加两种：失败、远端被改过。**（对 28、29、31）
34. **“不在”不等于“关”。** 本地文件夹没了，插件不能因此把线上的撤掉，只认意愿。（对 30、35）
35. **插件卸了再装，靠记录接上。** 地址和对应的快照都在实况事实里。（对 30）

### 记录和库本身

36. **说明的改动进管理日志。** 说明不在是有名字的状态。（对 34）
37. **软件服从库声明的格式版本。** 软件不悄悄改库，升级是主人的显式动作，记进管理日志。（对 36）
38. **抹除按号不按名。** 抹除事实是一份除名单，列的是条目号和事实号，同步到另一份副本时照单删除，不然并集合并会把抹掉的东西带回来。粒度到条目、单个快照、场景的附件、单条事实。（对 37、38）
39. **归档不是抹除。** 把五年前的记录压缩存放，只要视图仍然算上它们，就没有违反只增不改。（对 40）

| 按意思查找 | 日 39 | `CONTEXT.md` 已列为没定 |

## 5. 我自己拿不准的

**场景分段（修改 4）。** 它解决了“一次会话做两件事”，代价是场景多了一层结构。另一个办法是不加分段，靠 agent 把来自写精确，粗略来历错了由人补来历更正。我倾向加，因为长会话换话题是常态，但这是凭感觉。

**修改的数量。** 39 条修改里，大部分是给框架里已有的位置补词汇。真正改了定义的是场景（1、3、4）、过期（17、18）、线索（27、28）、合并规则（22、38）。v0 的事实词汇有 10 种，补完大约 16 种。词汇在变多，值得在写 v0.1 时看一遍能不能合并。
