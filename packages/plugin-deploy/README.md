# 部署插件 `deploy`

agent 用 `say deployable <库内路径>` 声明一样东西可以部署；主人用 `deploy on` / `deploy off` 开关决定它在不在线；开着的东西，目标上跟着库里当前的内容。设计见 `tmp/run-3/design.md` 第四节。

## 一个决定

插件只做一个判断：目标上**该有**什么。输入是三样：开关、是否在归档区、库里它的路径上有没有东西。

| 开关 | 在归档区 | 路径上有东西 | 目标上该有 |
| --- | --- | --- | --- |
| 开 | 否 | 有 | 当前内容，放在站点名 `siteName(当前路径)` 下 |
| 开 | 否 | 没有 | 什么都没有 |
| 开 | 是 | 不看 | 什么都没有 |
| 关 | 不看 | 不看 | 什么都没有 |

代码里是 `src/model.ts` 的 `want`。对账（`plan`）拿「该有」和记录里「目标上有」的比：该有的站点内容不同或没有，就发布；这样东西在目标上其余的站点（挪之前的旧名），在发布成功之后下线；该有的是什么都没有，就把它的站点全部下线。两边一样就什么都不做，所以对账跑几遍结果都一样。

`deploy sync`、开关、放入、挪、归档、取回之后，都是对受影响的那样东西跑同一个对账。`deploy sync` 对全部声明过的东西跑，并把当前目标上不属于任何声明的站点下线（声明随归档区一起被清掉的那种）。

## 状态

状态是「该有」和「目标上有」的纯函数（`statusOf`）：两边一致时按原因叫 在线、离线、已归档、不在；不一致时，该有东西叫 待发布，该是空的叫 待下线。

| 状态 | 开关 | 在归档区 | 路径上有东西 | 目标上 |
| --- | --- | --- | --- | --- |
| 离线 | 关 | 否 | 不看 | 没有它的站点 |
| 在线 | 开 | 否 | 有 | 恰是当前内容，在当前站点名下 |
| 待发布 | 开 | 否 | 有 | 别的内容、没有，或还在旧的站点名下 |
| 已归档 | 不看 | 是 | 不看 | 没有它的站点 |
| 待下线 | 关，或在归档区，或路径上没有东西 | | | 还有它的站点（上次下线失败） |
| 不在 | 开 | 否 | 没有 | 没有它的站点 |

## 状态 × 操作

每一格是：这次操作之后对账做了什么 → 目标答应时的状态（目标失败时的状态）。开关是主人命令；内容变了是 `put` 放入了不同的内容，或登记了在工具外改过的内容；挪是 `put <库内路径> --to <库内路径>`。

| 状态 ＼ 操作 | 开 | 关 | 内容变了 | 归档 | 取回 | 挪 |
| --- | --- | --- | --- | --- | --- | --- |
| 离线 | 发布 → 在线（待发布） | 不动 → 离线 | 不动 → 离线 | 不动 → 已归档 | 内核什么都不动（本来就在原处）→ 离线 | 记下新路径，不动 → 离线 |
| 在线 | 不动 → 在线 | 下线 → 离线（待下线） | 发布新内容 → 在线（待发布，线上还是旧的一版） | 下线 → 已归档（待下线） | 内核什么都不动 → 在线 | 在新站点名下发布，再下线旧名 → 在线（待发布，旧名照旧在线） |
| 待发布 | 发布 → 在线（待发布） | 下线它在目标上的站点 → 离线（待下线） | 发布 → 在线（待发布） | 下线它在目标上的站点 → 已归档（待下线） | 内核什么都不动；发布 → 在线（待发布） | 在新站点名下发布，再下线旧名 → 在线（待发布） |
| 已归档 | 记下开关，不动 → 已归档 | 记下开关，不动 → 已归档 | 不适用：归档区里的东西不能放入（`outside-library`） | 内核什么都不动 → 已归档 | 开关开：发布 → 在线（待发布）；开关关：不动 → 离线 | 不适用：归档区里的东西不能挪（`outside-library`） |
| 待下线 | 原因是开关关：发布并下线旧的 → 在线（待发布）；原因是归档或不在：再下线 → 已归档 / 不在（待下线） | 再下线 → 离线 / 已归档（待下线） | 原因是不在：发布并下线旧的 → 在线（待发布）；原因是开关关：再下线 → 离线（待下线） | 再下线 → 已归档（待下线） | 原因是归档：开关开则发布并下线旧的 → 在线（待发布），开关关则再下线 → 离线（待下线）；否则内核什么都不动，再下线 | 原因是开关关：记下新路径，再下线旧名 → 离线（待下线）；原因是不在：不适用，没有东西可挪 |
| 不在 | 不动 → 不在 | 不动 → 离线 | 路径上又有了东西：发布 → 在线（待发布） | 不适用：没有东西可归档（`no-such-file`） | 不适用：它不在归档区 | 不适用：没有东西可挪（`no-such-file`） |

声明（`say deployable`）是入口：新的一样东西从 离线 开始。归档区被清掉时（`archive purge`），在那里的声明一起去掉。

`test/model.test.ts` 逐格跑这张表。

## 站点名

从库内路径算出，内容怎么变都不变：小写，非 `a-z0-9` 的连续字符换成一个 `-`。路径本来就只由小写字母、数字、单个 `-` 和 `/` 组成时就是这个结果（`sites/shop` → `sites-shop`）；否则（大写、中文、别的符号）后面加路径的 sha256 前 6 位，免得两个路径撞名（`网站/首页` → `site-1c2f3a`）。最长 58 个字符，超了就截断并加那 6 位。两个干净的路径仍可能撞名（`a/b` 和 `a-b`）：后来的那个发布时以「站点名已被占用」失败，停在 待发布。

## 目标

目标是一个接口：`publish(站点名, 内容目录) → { url }`、`unpublish(站点名)`。发布前，插件把这样东西算进指纹的文件复制到缓存目录下的一个临时目录（不带 `.pneuma-item`），核对指纹和对账时算的一样，再交给目标。

- `dir`：`<目录>/<站点名>/…`，加一个 `<目录>/index.json`，列出在线的站点、指纹和库内路径。先复制到 `.tmp-` 开头的名字再改名换上。目录不能在库里，也不能包含库。
- `command`：主人配一条发布命令和一条下线命令，`{dir}`、`{name}` 换成内容目录和站点名（下线时 `{dir}` 是一个空目录）。命令按 shell 的引号规则切成参数，不经 shell 运行；工作目录是库的根目录；超时缺省 120 秒。可以配地址模板，比如 `https://{name}.pages.dev`。

## 存放

都在 `.pneuma-base/deploy/` 下，本体：

| 路径 | 内容 |
| --- | --- |
| `config.json` | 目标。`deploy target set` 先写临时名再改名换上 |
| `facts/` | 每次写入一个名字唯一、写完不动的 jsonl 文件：声明、开关、挪、去掉、发布、下线 |

「目标上有什么」来自 `facts/` 里对当前目标（按目标的标识区分）的发布和下线记录。换了目标，旧目标上的站点不算，开着的东西都成了 待发布，`deploy sync` 把它们发到新目标；旧目标上的不会被撤下。缓存目录里只有发布时的临时目录，用完就删。

## 命令

| 命令 | 谁能用 | 做什么 |
| --- | --- | --- |
| `deploy on <库内路径>` | 只有主人 | 打开开关并发布 |
| `deploy off <库内路径>` | 只有主人 | 关上开关并下线 |
| `deploy target set --kind dir --to <目录>` | 只有主人 | 配本地目录目标 |
| `deploy target set --kind command --publish "<命令>" --unpublish "<命令>" [--url <模板>] [--timeout <秒>]` | 只有主人 | 配命令目标 |
| `deploy sync` | 主人和 agent | 把全部声明过的东西对一遍 |
| `deploy list` | 主人和 agent | 列出声明过的东西、状态和地址 |

都不是破坏性的。对外发布是对外的动作，所以开关和目标只给主人：内核的门只拦破坏性的命令，这几条由插件自己看上下文，行动者是 agent、或会话来自 agent 产品的环境变量时，以 `agent-session` 拒绝。
