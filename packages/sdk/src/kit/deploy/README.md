# 部署库 `deployPlugin`

`@pneuma-base/sdk/kit` 里的部署库：给它一个插件名和一种或几种**目标**，它交回一个完整的部署插件。主人在它的页上连接一个部署目标，把一样东西发布、取消发布；agent 用 `say deployable <库内路径>` 声明一样东西可部署，是否发布由主人决定；开着的东西，目标上跟着库里当前的内容。和目标无关的都在库里：声明和它跟着挪、归档、取消归档、清掉，主人的开关，对账，记录，命令，页面和条目面板里的一节，说明里的一段。一个部署插件只写它的目标。

```ts
import { defineTarget, deployPlugin } from '@pneuma-base/sdk/kit'

const exampleTarget = defineTarget({
  kind: 'example',
  label: '示例服务',
  icon: 'cloud',
  params: [{ name: 'project', hint: '项目', kind: 'value', required: true }],
  secrets: [{ name: 'token', description: '示例服务的令牌' }],
  asked: { name: 'token', hint: '令牌' },
  async configure({ project }, ctx, typed) {
    const token = (await typed()) ?? (await ctx.secrets.get('token'))
    if (token === null) return { ok: false, reason: 'no-key', text: '没有令牌。' }
    // 用 token 问一次服务；答不上来就拒绝，什么都不存。
    return { ok: true, config: { project } }
  },
  open: (config, env) => ({ /* key, label, publish, remove；publish 里 await env.secret('token') */ }),
})

export default deployPlugin('example', exampleTarget)
```

自带的 `deploy` 插件是 `deployPlugin('deploy', [cloudflareTarget, selfHostedTarget, folderTarget, commandTarget])`，见 `packages/plugin-deploy`。库不导入内核：它对库的读写都经上下文的 `tools`，用存储的词（`tools.storage`：看一眼、一览、取内容、读、自己的记录处），插件契约第 2 版。一个库里同时只装一个部署插件：它们都认领 `say deployable`。

## 目标

目标的接口在 `target.ts`。`TargetAdapter` 是一种目标：

- `kind`：`<名字> target set --kind <kind>` 选它，也随它的配置存下。只有一种目标时可以不写 `--kind`。
- `formerly`，可选：它改名之前的 `kind`。存下的配置写着其中一个时，按这种目标打开，配置文件不改写。
- `label`：这种目标给人看的名字，用在对话框和菜单里：「本地文件夹」。
- `icon`，可选：目标那一行和找到的那几行的图标。
- `group`，可选：`{ name, choice }`。同组的几种合成一行「其他 <name>」（一个都没找到时就是「<name>」），对话框里按 `choice` 选；不在组里的是那一节菜单里的「<label>…」。
- `params`：`target set` 在 `--kind` 之后的开关，一份 `FlagParam[]`（`@pneuma-base/sdk` 的参数表）。命令行、帮助、页面上的对话框和 `configure` 之前的核对都从这里来。有几种目标时，几种都有的开关意思要一样；选定的那种必填的开关、不收别的种类的开关，由库核对。
- `form`，可选：对话框问的开关和次序；没写就是必填的那些。
- `secrets`：它读的密钥，`{ name, description, optional? }`。库把它们声明成插件的 `secrets`，所以 `pneuma-base secret set <名字> <密钥名>` 和配置页认得。目标从不在开关里要密钥。
- `asked`，可选：`{ name, hint }`，`target set` 不显示地读一次的密钥，`name` 是 `secrets` 里的一个。页面的对话框把它放在最后，经标准输入交给命令。`configure` 用第三个参数 `typed()` 读它；读到了、`configure` 又答应了，库把它存成这台机器上的那个密钥。它不进配置、记录和答复。几种目标都有 `asked` 时要是同一个名字。
- `found(ctx)`，可选：这台机器上找得到的这种目标，每个 `{ label, values }`，`values` 是连接它的 `target set` 开关，不用填什么。只读找它们要读的；抛错算一个都没有。
- `cognition`，可选：连着这种目标时插件的认知段后面多的一段（`onDescribe`），说发布的东西要满足什么。
- `views`，可选：它自己的页，`{ name, title, icon }`，和部署库的页共用导航里的一项，视图编号 `<插件名>.<name>`；画它的是打开的目标的 `view.pages[name]`。
- `configure(值, 上下文, typed)`：把核过的值变成要存的配置（一个 JSON 对象），或者说哪里不对；理由是 `usage` 的算用法错误。目标答不上来也是拒绝，这时什么都不存。可以带 `note`，一句给主人的话，代替对没设的必需密钥的提醒。
- `open(配置, { ctx, scratch, plugin, secret })`：在边界上解析存下的配置，交回这次钩子或命令用的 `Target`；读不懂就抛错。`plugin` 是插件名。`secret(名字)` 读主人在这台机器上设的密钥；必需的没设时它拒绝，说用哪条命令设，这次发布或取消发布就以这句话失败；可选的没设时读出 null。用 `defineTarget` 写时，`secret` 只收 `secrets` 里的名字，可选的类型带 null；`open` 的返回写成 `Target<细节的类型>`，`view` 里的函数拿到的细节就有这个类型。

`Target` 是配好的一个目标：

- `key`：记录按它区分目标，换了 key，记录里旧目标上的站点不算。
- `label`：目标那一行写什么：主机名、文件夹，或这种目标自己的话。
- `local`，可选：`label` 是这台机器上的一个路径，那一行显示最后一段，要时显示全部。
- `settings`，可选：连接之后还能改的开关，每个 `{ flag, hint, value }` 是那一行菜单里的「<hint>…」，用存下的开关再跑一次 `target set`，只问这一个，填好 `value`。
- `publish(站点名, 目录, meta)` → `{ url }`、`remove(站点名)`。`meta` 带内容的编号、库内路径、时刻，和目录里的文件（存储的内容规则算进的那些，按路径的 UTF-8 字节排好）。符号链接、设备不算内容，复制件里没有它们。
- `siteName(库内路径)`，可选：没有就用下面「站点名」的规则。
- `identify(文件)`，可选：内容的编号。没有就用存储给的指纹。编号进记录、和目标报的比。给它的文件是库外的一份复制件：每次要编号都把内容整个读一遍、复制一遍。
- `serving(站点名, { detail })`，可选：它对这些站点知道什么，按站点给：在那里给这个库服务的内容（没在服务是 null）、地址，和 `detail`，它自己知道的别的（它的数字、名字归谁），交给它自己的视图。没答的站点算它既没服务也不知道。`detail` 为真时答复要画出来（部署库的页、目标自己的页、条目面板），为假时是钩子和命令，只看内容和地址，所以只给页面看的贵的数据只在为真时取。没有要问的站点时不问。
- `view`，可选：条目面板里地址下面的字段（`fields`，正常的值不画），页面上部署库的块前面和后面加的块（`before`、`page`），目标自己每一页的块（`pages`），面板末尾加的块（`item`），一行的标记（`mark`，比如名字被别人占着；null 是没有）；块可以是 `custom` 块，插件的页面目录由 `deployPlugin` 的 `ui` 给出。`refresh` 是页面隔几秒重取，null 是不重取；没写时目标有 `serving` 就是 30 秒，否则不重取。每个函数拿到的 `Look` 带 `detail`：`serving` 对它的站点说的，先取它在服务的那个站点（优先它的站点名），再取它的路径（归档了就是原来的路径）的站点名；没有就是 null，页面和面板之外也是 null。
- `close()`，可选：这个 `Target` 为之打开的钩子、命令或视图结束时调一次，失败了也调。登录服务的目标在这里退出登录，所以一次登录只用在一次运行里；它抛的错不影响答复。
- 什么时候问：一页（部署库的或目标自己的）先为全部声明过的东西问一次 `serving`，再调视图的函数；条目面板先为它那样东西问，再调 `fields` 和 `item`。所以视图的函数总在它画的那次答复之后，拿到的是那次的细节。
- 目标自己的块要和部署库的一样时，用 `@pneuma-base/sdk/kit` 导出的 `STATUS`（每种状态的标签）和 `switchAction(插件名, look)`（那样东西的开关，归档了又关着的是 null）。状态的值是 `published`、`pending`、`unpublished`、`pending-unpublish`、`archived`、`missing`、`unknown`。

## 一个决定

库只做一个判断：目标上**该有**什么。输入是三样：开关、是否在归档区、库里它的路径上有没有东西。

| 开关 | 在归档区 | 路径上有东西 | 目标上该有 |
| --- | --- | --- | --- |
| 开 | 否 | 有 | 当前内容，放在当前路径的站点名下 |
| 开 | 否 | 没有 | 什么都没有 |
| 开 | 是 | 不看 | 什么都没有 |
| 关 | 不看 | 不看 | 什么都没有 |

代码里是 `model.ts` 的 `want`。对账（`plan`）拿「该有」和「目标上有」的比：该有的站点内容不同或没有，就发布；这样东西在目标上其余的站点（挪之前的旧名），在发布成功之后取消发布；该有的是什么都没有，就把它的站点全部取消发布。两边一样就什么都不做，所以对账跑几遍结果都一样。

`<名字> sync`、开关、放入、挪、归档、取消归档之后，都是对受影响的那样东西跑同一个对账。`<名字> sync` 对全部声明过的东西跑，并把当前目标上不属于任何声明的站点取消发布（声明随归档区一起被清掉的那种）。

## 状态

状态是「该有」和「目标上有」的纯函数（`statusOf`）：两边一致时按原因叫 已发布、未发布、已归档、条目缺失；不一致时，该有东西叫 待发布，该是空的叫 待取消发布。

| 状态 | 开关 | 在归档区 | 路径上有东西 | 目标上 |
| --- | --- | --- | --- | --- |
| 未发布 | 关 | 否 | 不看 | 没有它的站点 |
| 已发布 | 开 | 否 | 有 | 恰是当前内容，在当前站点名下 |
| 待发布 | 开 | 否 | 有 | 别的内容、没有，或还在旧的站点名下 |
| 已归档 | 不看 | 是 | 不看 | 没有它的站点 |
| 待取消发布 | 关，或在归档区，或路径上没有东西 | | | 还有它的站点（上次取消发布失败） |
| 条目缺失 | 开 | 否 | 没有 | 没有它的站点 |

会报告自己在服务什么的目标读不到时（`serving` 抛错），状态是 **状态未知**：这次什么都不发布、不取消发布，`check` 和页面说读不到的原因。

## 状态 × 操作

每一格是：这次操作之后对账做了什么 → 目标答应时的状态（目标失败时的状态）。发布、取消发布是主人命令；内容修改是 `put` 放入了不同的内容，或登记了在工具外改过的内容；移动是 `put <库内路径> --to <库内路径>`。

| 状态 ＼ 操作 | 发布 | 取消发布 | 内容修改 | 归档 | 取消归档 | 移动 |
| --- | --- | --- | --- | --- | --- | --- |
| 未发布 | 发布 → 已发布（待发布） | 不动 → 未发布 | 不动 → 未发布 | 不动 → 已归档 | 内核什么都不动（本来就在原处）→ 未发布 | 记下新路径，不动 → 未发布 |
| 已发布 | 不动 → 已发布 | 取消发布 → 未发布（待取消发布） | 发布新内容 → 已发布（待发布，目标上还是旧的一版） | 取消发布 → 已归档（待取消发布） | 内核什么都不动 → 已发布 | 在新站点名下发布，再取消发布旧名 → 已发布（待发布，旧名照旧已发布） |
| 待发布 | 发布 → 已发布（待发布） | 取消发布它在目标上的站点 → 未发布（待取消发布） | 发布 → 已发布（待发布） | 取消发布它在目标上的站点 → 已归档（待取消发布） | 内核什么都不动；发布 → 已发布（待发布） | 在新站点名下发布，再取消发布旧名 → 已发布（待发布） |
| 已归档 | 记下开关，不动 → 已归档 | 记下开关，不动 → 已归档 | 不适用：归档区里的东西不能放入（`outside-library`） | 内核什么都不动 → 已归档 | 开关开：发布 → 已发布（待发布）；开关关：不动 → 未发布 | 不适用：归档区里的东西不能挪（`outside-library`） |
| 待取消发布 | 原因是开关关：发布并取消发布旧的 → 已发布（待发布）；原因是归档或条目缺失：再取消发布 → 已归档 / 条目缺失（待取消发布） | 再取消发布 → 未发布 / 已归档（待取消发布） | 原因是条目缺失：发布并取消发布旧的 → 已发布（待发布）；原因是开关关：再取消发布 → 未发布（待取消发布） | 再取消发布 → 已归档（待取消发布） | 原因是归档：开关开则发布并取消发布旧的 → 已发布（待发布），开关关则再取消发布 → 未发布（待取消发布）；否则内核什么都不动，再取消发布 | 原因是开关关：记下新路径，再取消发布旧名 → 未发布（待取消发布）；原因是条目缺失：不适用，没有东西可挪 |
| 条目缺失 | 不动 → 条目缺失 | 不动 → 未发布 | 路径上又有了东西：发布 → 已发布（待发布） | 不适用：没有东西可归档（`no-such-file`） | 不适用：它不在归档区 | 不适用：没有东西可挪（`no-such-file`） |

声明是入口：新的一样东西从 未发布 开始。agent 用 `say deployable` 声明；主人对没声明的东西 `<名字> publish`，先记声明再记开关。归档区被清掉时（`archive purge`，`onPurged`），先把那里的声明在目标上剩下的站点取消发布，再去掉声明。

`packages/sdk/test/kit-model.test.ts` 在纯函数上逐格跑这张表；`packages/plugin-deploy/test/kit.test.ts` 经真的内核、对一个放在内存里的目标逐格跑一遍。

## 「目标上有」从哪来

- 目标没有 `serving`：来自插件自己的记录里对当前目标（按 `key`）的发布和取消发布。目标背后被人删掉的站点，它看不见。
- 目标有 `serving`：来自目标。问的是这样东西的路径（归档了就是原来的路径）的站点名，和记录里它的站点名，记录里归另一个还在的声明的站点名不问；一页里全部东西的站点名一起问一次。内容不是 null 的才算目标上有。对账前先把记录对齐目标：目标上有、记录里没有的记成发布（发布到了目标、还没记下就断了的那种），记录里有、目标上没有的记成取消发布。所以 `<名字> sync` 修得好断在一半的发布和被人在目标那边删掉的站点，之后的挪也撤得下旧名。取消发布没人声明的站点时，目标说它没在服务的只记取消发布，不再去撤。

发布前，库把这样东西算进内容的文件复制到缓存目录下的一个临时目录（单个文件保留文件名）。哪些算进内容由存储按内容规则算：带标记的目录要存储的清单（`content` 带 `manifest`，一页至多一万条，一样东西至多 5000 个文件），每条是相对它的路径、指纹和大小，不带 `.pneuma-item`、噪音和它里面的 `.gitignore` 排除的；库不走这个目录。每个文件用存储的 `read` 写到临时目录，再拿它的 sha256 和清单里的指纹比；不同就是读的时候它又变了，不发布，说它正在被改动。核对复制件的编号就是对账时算的，再交给目标；不同也一样不发布。超过 5000 个文件的目录存储答 `too_many`：不发布，也不取消发布目标上的旧版，说它至少有多少个文件；状态是 待发布。

## 站点名

缺省从库内路径算出，内容怎么变都不变：小写，非 `a-z0-9` 的连续字符换成一个 `-`。路径本来就只由小写字母、数字、单个 `-` 和 `/` 组成时就是这个结果（`sites/shop` → `sites-shop`）；否则（大写、中文、别的符号）后面加路径的 sha256 前 6 位，免得两个路径撞名（`网站/首页` → `site-1c2f3a`）。最长 58 个字符，超了就截断并加那 6 位。两个干净的路径仍可能撞名（`a/b` 和 `a-b`）：后来的那个发布时以「站点名称 … 已被 … 占用」失败，停在 待发布。目标的 `siteName` 可以换掉这条规则，比如加上主人的前缀。

## 存放

都在 `.pneuma-base/<名字>/` 下，本体：

| 路径 | 内容 |
| --- | --- |
| `config.json` | 目标：`{ format: 1, target: { kind, …目标自己的配置 }, given }`。`given` 是主人给 `target set` 的开关（没有读进来的密钥），「更换部署目标…」从它开始填，改一个设置时和改的那个一起再跑 `target set`。`<名字> target set` 经存储整份写入，带着读到的那一版的令牌；`<名字> target remove` 删掉它 |
| `facts/` | 记录处的事实，记录库 `facts`：声明、开关、挪、去掉、发布、取消发布，每次一批，写完不动。以前的版本直接写在 `facts/` 下的 jsonl 文件照样读。读不懂的事实原样留着，`check` 里列出 |

换了目标，旧目标上的站点不算，开着的东西都成了 待发布，`<名字> sync` 把它们发到新目标；旧目标上的不会被取消发布。目标的 `kind` 改过名时，存下的旧名经 `formerly` 照样打开。缓存目录里只有发布时的临时目录，用完就删。

## 命令

| 命令 | 谁能用 | 做什么 |
| --- | --- | --- |
| `<名字> publish <库内路径>` | 只有主人 | 打开开关并发布；没声明过的先记声明 |
| `<名字> unpublish <库内路径>` | 只有主人 | 关上开关并取消发布；没声明过的以 `not-declared` 拒绝 |
| `<名字> sync` | 主人和 agent | 把全部声明过的东西对一遍 |
| `<名字> list` | 主人和 agent，只读 | 列出声明过的东西、状态和地址 |
| `<名字> target set [--kind <kind>] <目标的开关>` | 只有主人 | 连接目标；目标答不上来时什么都不存 |
| `<名字> target list` | 主人和 agent，只读 | 连着的目标，和这台机器上找到的，各带连接它的命令 |
| `<名字> target remove` | 只有主人 | 断开连接；已发布的不取消发布，开关都留着 |

每条都有参数表。都不是破坏性的。对外发布是对外的动作，所以开关和目标只给主人：这几条声明 `ownerOnly`，内核的门在 agent 的会话里以 `agent-session` 拒绝。`target set` 的活动行按 `host`、`origin`、`admin`、`to` 里先给的那个起名，都没有时是「自定义命令」。

答复说事实，不叫人去跑命令：`已发布 sites/shop → https://…`、`已取消发布 sites/shop。`、`已连接 space.example.com。3 个待发布。`、`已断开连接 space.example.com。2 个已发布的条目未取消发布。`。开关在目标失败时照样记下，答复以 `publish-failed` / `unpublish-failed` 或 `no-target` 拒绝，说开关怎样了、为什么没发布。agent 的放入、挪、归档让目标失败时，放入照样成功，答复的 `problems` 里说它无需重做、发布等主人运行 `<名字> sync`。

`plugin disable <名字>` 在目标上还有它的站点时拒绝，说有几个已发布、先用 `<名字> unpublish` 取消发布；主人用 `--force`（界面里是提示上的「仍然停用」）照样停用时，答复列出仍发布在目标上的那些。

## 页面

页 `<名字>.sites`，目标自己的页和它共用导航里的一项。

**没连目标。** 只有一节「部署目标」：这台机器上找到的每个目标一行，带「连接」（一下就连接，不问什么）；每组目标一行「其他 <组名>」，「连接…」打开对话框，先选组里哪一种，再问那一种的开关，`asked` 的密钥在最后；不在组里的几种在这一节的菜单里，一行都没有时它们就是这几行。

**连着目标。** 页头是「发布条目」，选一样登记过、还没声明的目录东西（新的在前，最多 200 个，多于 5 个时是可以筛的列表），声明和发布一起做；有东西待发布或待取消发布时另有「重试」（`<名字> sync`）。下面一行是目标，菜单里是「更换部署目标…」、每个设置的「<hint>…」和「断开连接」。再下面每样声明过、在库里的东西一行（还待取消发布的归档的也在）：名字点开面板，下面是它所在的文件夹，后面是地址（网址可以点开，都可以复制），最后是开关。没有时写「暂无可部署的条目」。副标题是有地址的有几个：「3 个已发布」。

一行不对劲时带一个标记，悬停说为什么：待发布、待取消发布、条目缺失（警告），状态未知（错误），和目标自己的 `mark`。已发布、未发布什么都不标。目标读不到时，目标那一行标「无法连接」。

**条目面板。** 声明过的东西：标记和原因、地址在一行，目标的字段里有话说的，目标的块；开关在面板的菜单里。还没声明、连着目标、在库里的目录东西：菜单里一项「发布…」，先问「发布 shop 到 space.example.com？」。别的什么都不加；什么都不说的一节不画。

页面按目标的 `refresh` 重取。几种目标的页不能重名，也不能叫 `sites`，否则 `deployPlugin` 抛错。
