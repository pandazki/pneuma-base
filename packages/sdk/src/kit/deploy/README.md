# 部署库 `deployPlugin`

`@pneuma-base/sdk/kit` 里的部署库：给它一个插件名和一个或几个**目标**，它交回一个完整的部署插件。agent 用 `say deployable <库内路径>` 声明一样东西可以部署；主人用 `<名字> on` / `<名字> off` 开关决定它在不在线；开着的东西，目标上跟着库里当前的内容。和目标无关的都在库里：声明和它跟着挪、归档、取回、清掉，主人的开关，对账，记录，命令，页面和条目面板里的一节，说明里的一段。一个部署插件只写它的目标。

```ts
import { deployPlugin } from '@pneuma-base/sdk/kit'
export default deployPlugin('space', spaceTarget, { title: 'PneumaSpace' })
```

自带的 `deploy` 插件就是 `deployPlugin('deploy', [dirTarget, commandTarget])`，见 `packages/plugin-deploy`。库不导入内核：它对库的读写都经上下文的 `tools`。一个库里同时只装一个部署插件：它们都认领 `say deployable`。

## 目标

目标的接口在 `target.ts`。`TargetAdapter` 是一种目标：

- `kind`：`<名字> target set --kind <kind>` 选它，也随它的配置存下。只有一种目标时可以不写 `--kind`。
- `label`：给人看的「发布到哪种地方」，拼成命令的说明 `配部署目标：<label>`。
- `usage`、`flags`：`target set` 在 `--kind` 之后的参数，可选的写在方括号里。没配目标时的提示只列必填的那些。
- `form`：页面上设这种目标的按钮，每个输入和一个参数同名。
- `secrets`：它要用的密钥，只是名字和给人看的说明，库现在不读。
- `configure(参数, 上下文)`：把参数变成要存的配置（一个 JSON 对象），或者说哪里不对；理由是 `usage` 的算用法错误。
- `open(配置, { ctx, scratch })`：在边界上解析存下的配置，交回这次钩子或命令用的 `Target`；读不懂就抛错。

`Target` 是配好的一个目标：

- `key`：记录按它区分目标，换了 key，记录里旧目标上的站点不算。
- `label`：给人看的「什么、在哪」。
- `publish(站点名, 目录, meta)` → `{ url }`、`remove(站点名)`。`meta` 带内容的编号、库内路径、时刻，和目录里的文件（按路径的 UTF-8 字节排好）。
- `siteName(库内路径)`，可选：没有就用下面「站点名」的规则。
- `identify(文件)`，可选：内容的编号。没有就用内核的指纹。编号进记录、和目标报的比。
- `serving(站点名)`，可选：这些站点里它现在真的在给这个库服务哪些，各是什么内容、在什么地址。
- `view`，可选：页面表格后面加的列（`columns`、`cells`），条目面板里加的字段（`fields`），页面和面板末尾加的块（`page`、`item`，可以是 `custom` 块；插件的页面目录由 `deployPlugin` 的 `ui` 给出）。

## 一个决定

库只做一个判断：目标上**该有**什么。输入是三样：开关、是否在归档区、库里它的路径上有没有东西。

| 开关 | 在归档区 | 路径上有东西 | 目标上该有 |
| --- | --- | --- | --- |
| 开 | 否 | 有 | 当前内容，放在当前路径的站点名下 |
| 开 | 否 | 没有 | 什么都没有 |
| 开 | 是 | 不看 | 什么都没有 |
| 关 | 不看 | 不看 | 什么都没有 |

代码里是 `model.ts` 的 `want`。对账（`plan`）拿「该有」和「目标上有」的比：该有的站点内容不同或没有，就发布；这样东西在目标上其余的站点（挪之前的旧名），在发布成功之后下线；该有的是什么都没有，就把它的站点全部下线。两边一样就什么都不做，所以对账跑几遍结果都一样。

`<名字> sync`、开关、放入、挪、归档、取回之后，都是对受影响的那样东西跑同一个对账。`<名字> sync` 对全部声明过的东西跑，并把当前目标上不属于任何声明的站点下线（声明随归档区一起被清掉的那种）。

## 状态

状态是「该有」和「目标上有」的纯函数（`statusOf`）：两边一致时按原因叫 在线、离线、已归档、不在；不一致时，该有东西叫 待发布，该是空的叫 待下线。

| 状态 | 开关 | 在归档区 | 路径上有东西 | 目标上 |
| --- | --- | --- | --- | --- |
| 离线 | 关 | 否 | 不看 | 没有它的站点 |
| 在线 | 开 | 否 | 有 | 恰是当前内容，在当前站点名下 |
| 待发布 | 开 | 否 | 有 | 别的内容、没有，或还在旧的站点名下 |
| 已归档 | 不看 | 是 | 不看 | 没有它的站点 |
| 待下线 | 关，或在归档区，或路径上没有东西 | | | 还有它的站点（上次下线失败） |
| 不在 | 开 | 否 | 没有 | 没有它的站点 |

会报告自己在服务什么的目标读不到时（`serving` 抛错），状态是 **不知道**：这次什么都不发布、不下线，`check` 和页面说读不到的原因。

## 状态 × 操作

每一格是：这次操作之后对账做了什么 → 目标答应时的状态（目标失败时的状态）。开关是主人命令；内容变了是 `put` 放入了不同的内容，或登记了在工具外改过的内容；挪是 `put <库内路径> --to <库内路径>`。

| 状态 ＼ 操作 | 开 | 关 | 内容变了 | 归档 | 取回 | 挪 |
| --- | --- | --- | --- | --- | --- | --- |
| 离线 | 发布 → 在线（待发布） | 不动 → 离线 | 不动 → 离线 | 不动 → 已归档 | 内核什么都不动（本来就在原处）→ 离线 | 记下新路径，不动 → 离线 |
| 在线 | 不动 → 在线 | 下线 → 离线（待下线） | 发布新内容 → 在线（待发布，线上还是旧的一版） | 下线 → 已归档（待下线） | 内核什么都不动 → 在线 | 在新站点名下发布，再下线旧名 → 在线（待发布，旧名照旧在线） |
| 待发布 | 发布 → 在线（待发布） | 下线它在目标上的站点 → 离线（待下线） | 发布 → 在线（待发布） | 下线它在目标上的站点 → 已归档（待下线） | 内核什么都不动；发布 → 在线（待发布） | 在新站点名下发布，再下线旧名 → 在线（待发布） |
| 已归档 | 记下开关，不动 → 已归档 | 记下开关，不动 → 已归档 | 不适用：归档区里的东西不能放入（`outside-library`） | 内核什么都不动 → 已归档 | 开关开：发布 → 在线（待发布）；开关关：不动 → 离线 | 不适用：归档区里的东西不能挪（`outside-library`） |
| 待下线 | 原因是开关关：发布并下线旧的 → 在线（待发布）；原因是归档或不在：再下线 → 已归档 / 不在（待下线） | 再下线 → 离线 / 已归档（待下线） | 原因是不在：发布并下线旧的 → 在线（待发布）；原因是开关关：再下线 → 离线（待下线） | 再下线 → 已归档（待下线） | 原因是归档：开关开则发布并下线旧的 → 在线（待发布），开关关则再下线 → 离线（待下线）；否则内核什么都不动，再下线 | 原因是开关关：记下新路径，再下线旧名 → 离线（待下线）；原因是不在：不适用，没有东西可挪 |
| 不在 | 不动 → 不在 | 不动 → 离线 | 路径上又有了东西：发布 → 在线（待发布） | 不适用：没有东西可归档（`no-such-file`） | 不适用：它不在归档区 | 不适用：没有东西可挪（`no-such-file`） |

声明（`say deployable`）是入口：新的一样东西从 离线 开始。归档区被清掉时（`archive purge`，`onPurged`），先把那里的声明在目标上剩下的站点撤下，再去掉声明。

`packages/sdk/test/kit-model.test.ts` 在纯函数上逐格跑这张表；`packages/plugin-deploy/test/kit.test.ts` 经真的内核、对一个放在内存里的目标逐格跑一遍。

## 「目标上有」从哪来

- 目标没有 `serving`：来自插件自己的记录里对当前目标（按 `key`）的发布和下线。目标背后被人删掉的站点，它看不见。
- 目标有 `serving`：来自目标。问的是这样东西的路径（归档了就是原来的路径）的站点名，和记录里它的站点名；记录里归另一个还在的声明的站点名不算它的。对账前先把记录对齐目标：目标上有、记录里没有的记成发布（发布到了目标、还没记下就断了的那种），记录里有、目标上没有的记成下线。所以 `<名字> sync` 修得好断在一半的发布和被人在目标那边删掉的站点，之后的挪也撤得下旧名。下线没人声明的站点时，目标说它没在服务的只记下线，不再去撤。

发布前，库把这样东西算进内容的文件复制到缓存目录下的一个临时目录（单个文件保留文件名，带标记的目录不带 `.pneuma-item`），核对复制件的编号就是对账时算的，再交给目标；不同就不发布，说它正在被改动。

## 站点名

缺省从库内路径算出，内容怎么变都不变：小写，非 `a-z0-9` 的连续字符换成一个 `-`。路径本来就只由小写字母、数字、单个 `-` 和 `/` 组成时就是这个结果（`sites/shop` → `sites-shop`）；否则（大写、中文、别的符号）后面加路径的 sha256 前 6 位，免得两个路径撞名（`网站/首页` → `site-1c2f3a`）。最长 58 个字符，超了就截断并加那 6 位。两个干净的路径仍可能撞名（`a/b` 和 `a-b`）：后来的那个发布时以「站点名已被占用」失败，停在 待发布。目标的 `siteName` 可以换掉这条规则，比如加上主人的前缀。

## 存放

都在 `.pneuma-base/<名字>/` 下，本体：

| 路径 | 内容 |
| --- | --- |
| `config.json` | 目标：`{ format: 1, target: { kind, …目标自己的配置 } }`。`<名字> target set` 先写临时名再改名换上 |
| `facts/` | 每次写入一个名字唯一、写完不动的 jsonl 文件：声明、开关、挪、去掉、发布、下线。读不懂的行原样留着，`check` 里列出 |

换了目标，旧目标上的站点不算，开着的东西都成了 待发布，`<名字> sync` 把它们发到新目标；旧目标上的不会被撤下。缓存目录里只有发布时的临时目录，用完就删。

## 命令

| 命令 | 谁能用 | 做什么 |
| --- | --- | --- |
| `<名字> on <库内路径>` | 只有主人 | 打开开关并发布 |
| `<名字> off <库内路径>` | 只有主人 | 关上开关并下线 |
| `<名字> target set [--kind <kind>] <目标的参数>` | 只有主人 | 配目标 |
| `<名字> sync` | 主人和 agent | 把全部声明过的东西对一遍 |
| `<名字> list` | 主人和 agent | 列出声明过的东西、状态和地址 |

都不是破坏性的。对外发布是对外的动作，所以开关和目标只给主人：这几条声明 `ownerOnly`，内核的门在 agent 的会话里以 `agent-session` 拒绝。开关在目标失败时照样记下，答复以 `publish-failed` / `unpublish-failed` 或 `no-target` 拒绝并说明现在的状态。agent 的放入、挪、归档让目标失败时，放入照样成功，答复的 `problems` 里说这不是它的放入出了问题、上线等主人运行 `<名字> sync`。

`plugin remove <名字>` 在目标上还有它的站点时拒绝，说有几样在线、先用 `<名字> off` 关上；主人用 `--anyway` 照样卸下时，答复列出留在线上的那些。

## 页面

页 `<名字>.sites`：目标和配每种目标的按钮；可部署的东西一张表，路径、状态、地址（网址可以点开，都可以复制）、目标加的列，每行一个开关，「对一遍」；目标加的块在最后。条目面板里的一节：状态、开关、地址、站点名、目标加的字段，状态的意思，开关按钮，目标加的块。
